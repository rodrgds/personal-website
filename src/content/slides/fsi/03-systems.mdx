<Slide title="Principles (1/2)">

## Saltzer and Schroeder, 1 to 5

<div class="cards" style="--n:3">
<div class="card" data-color="blue">

### Economy of mechanism

Only the functions you need, and the simplest mechanisms.

</div>
<div class="card" data-color="green">

### Fail-safe defaults

Conservative by default. On failure, **fail closed**, not open.

</div>
<div class="card" data-color="orange">

### Complete mediation

A policy for every resource, checked on **every access**. Web failure: IDOR.

</div>
<div class="card" data-color="purple">

### Open design

Security must not depend on hiding the mechanism. Only keys are secret.

</div>
<div class="card" data-color="red">

### Separation of privilege

Isolated compartments, each in its own trust domain.

</div>
</div>

<Notes>

These are Saltzer and Schroeder's ten principles, from 1975. The test asks you to recognize the names, so learn the list.

Economy of mechanism: no "nice to have" features or extra services. Less code, fewer bugs, easier validation.

Fail-safe defaults: a new user starts with minimum permissions, and on failure the system falls back to its locked state. The lecture's bad defaults: the FortiGate VPN default config allowed man-in-the-middle attacks, and Thomson and BT routers had a default Wi-Fi key you could compute.

Complete mediation: validate every access against the policy. The web counterexample is IDOR: change `id=123` in the URL and see someone else's account. In Linux, the OS mediates every memory access.

Open design: the mechanism is public; the only secrets are keys and passwords. Its opposite is security through obscurity.

Separation of privilege: compartments, so a compromise stays local.

</Notes>
</Slide>

<Slide title="Principles (2/2)">

## Saltzer and Schroeder, 6 to 10

<div class="cards" style="--n:3">
<div class="card" data-color="orange">

### Least privilege

Only what the role needs. Bad: **every service as root**. Good: app permissions on Android.

</div>
<div class="card" data-color="cyan">

### Least common mechanism

Share as little as possible, above all between privilege levels.

</div>
<div class="card" data-color="red">

### Defense in depth

Any mechanism can fail, so stack several. The "castle approach".

</div>
<div class="card" data-color="blue">

### Psychological acceptability

Easy enough that people use it correctly.

</div>
<div class="card" data-color="purple">

### Work factor, compromise recording

Attack cost versus gain. Log every breach.

</div>
</div>

<Notes>

Least privilege: every user, compartment or program gets only what its role needs. Breaking it amplifies the damage of any breach. Running every service as root is the classic sin.

Least common mechanism: minimize shared resources and shared access mechanisms, especially between users with different privilege levels. The examples: don't reuse your Facebook password on Sigarra, keep each user's data on a different file system, and don't let the web server and the database server share interfaces.

Defense in depth: never put all your trust in one mechanism. The bad example is a strong perimeter that assumes there are no internal threats.

The last three only get a name in the lecture. Compromise recording comes back later as logging and the reference monitor.

</Notes>
</Slide>

## Access control matrix

<Cols columns="1.15fr 1fr" gap={72} align="center">
<div>

| | R1 | R2 | R3 |
| --- | --- | --- | --- |
| <Mark at={2} type="highlight" color="orange">A1</Mark> | r | <Mark at={1} type="highlight" color="blue">rw</Mark> | - |
| <Mark at={2} type="highlight" color="orange">A2</Mark> | <Mark at={2} type="highlight" color="orange">rw</Mark> | <Mark at={1} type="highlight" color="blue"><Mark at={2} type="box" color="orange">-</Mark></Mark> | <Mark at={2} type="highlight" color="orange">r</Mark> |
| <Mark at={2} type="highlight" color="orange">A3</Mark> | r | <Mark at={1} type="highlight" color="blue">r</Mark> | r |

<p class="small muted">Actors in rows, resources in columns.</p>

</div>
<div>

<Step at={1}>

### ACL: one **column**

Stored next to each **resource**. A guest list. Inbound.

</Step>

<Step at={2}>

### Capabilities: one **row**

Stored next to each **actor**. A ticket. Outbound.

</Step>

</div>
</Cols>

<Notes>

Access control puts least privilege, complete mediation and separation of privilege into practice. An actor performs an operation on a resource, and the pair resource plus operation is a permission.

The matrix lists every possible access. Advantage: clarity, you can set any permission of any actor on any resource. Problem: the number of combinations, and it doesn't scale centrally.

**[→]** Store it by column and you get an access control list, a guest list: not on it, not in. Advantages: locality, permissions sit next to the resource, and isolation, few actors per resource. Disadvantage: to remove an actor, you must check every resource. Inbound, oriented to what is accessed.

**[→]** Store it by row and you get capabilities, a ticket each actor carries. The mirror image: to find who can reach a resource, you must check every actor. Outbound, oriented to who accesses.

</Notes>
</Slide>

<Slide title="RBAC and ABAC">

## RBAC and ABAC

<Cols columns="1fr 1fr" gap={72} align="start">
<div>

### RBAC

<p class="big">Actor → <strong>role</strong> → permissions</p>

Role to permissions: stable, like an **ACL**. Actor to role: dynamic, like **capabilities**.

</div>
<div>

<Step at={1}>

### ABAC

<p class="big">Attributes → <strong>engine</strong> → decision</p>

Actors and resources get attributes. The policy can use place, time or hierarchy. RBAC is a special case.

</Step>

</div>
</Cols>

<Notes>

RBAC, role-based access control, separates managing resources from managing actors by adding roles in the middle. The link from roles to permissions rarely changes and is run by whoever manages the resources, so it looks like an ACL. The link from actors to roles changes often and is run by whoever manages the users, so it looks like capabilities. The Unix file system is an example, as we'll see.

**[→]** ABAC, attribute-based access control. Actors and resources carry attributes, and a rule says, for example, "to access a resource with attribute A, you need attribute B". A dynamic engine receives both attributes and decides using the policy. That lets you write geographic, time-based or hierarchical policies. RBAC is the special case where the only attribute is the role.

</Notes>
</Slide>

<Slide title="The OS security model">

## The OS security model

<Reveal>

- Honest users and processes run **isolated** applications
- Attackers impersonate them to **escalate** permissions, break isolation or take resources
- The OS gives each one **virtual isolation**, despite shared hardware, by **mediating** every access
- Administering an OS means **configuring** that mediation well

</Reveal>

<Notes>

The OS shares storage, CPU, memory and network across many users and apps.

**[→]** Alice and Bob are honest. **[→]** Mallory and Darth try to pass as them, controlling users, processes or malicious files. Users and applications are both potential threats, and protection must hold even for programs that aren't running, since their state sits on shared disk and RAM.

**[→]** The OS keeps its isolation promise through access mediation. **[→]** The principles you just learned are the guide to configuring it.

</Notes>
</Slide>

<Slide title="Kernel mode, user mode">

## Kernel mode, user mode

<Cols columns="1fr 1fr" gap={72} align="start">
<div>

### CPU privilege levels

- **Intel rings:** ring 0 kernel, ring 3 apps
- **ARM:** EL0 apps, EL1 kernel, EL2 hypervisor, EL3 firmware

In practice two: **kernel** and **user**.

</div>
<div>

### Reference monitor

<Reveal>

- Guards the perimeter, the **syscalls**: complete mediation and recording
- Always present: if it dies, monitored processes die (**fail-safe**)
- **Simple**, so it can be validated (economy of mechanism)

</Reveal>

</div>
</Cols>

<Notes>

In kernel mode code can do almost anything; in user mode it has no direct access to resources. The hardware enforces this with privilege levels, defense in depth. Intel has four rings, but most systems use only 0 and 3. Any data crossing between the levels is attack surface.

The kernel has its own memory and only it runs privileged instructions: separation of privilege. User processes, drivers included, ask through system calls: least privilege. So the syscall entry points are the perimeter, guarded by a reference monitor. **[→]** It sees every syscall, so it gives complete mediation and compromise recording. **[→]** It is always present: if it terminates, every monitored process must terminate too, which is fail-safe defaults. **[→]** And it must be simpler than the whole system so you can analyze it, economy of mechanism.

</Notes>
</Slide>

<Slide title="A syscall, step by step">

## The path of a syscall

<Cols columns="1.2fr 1fr" gap={56} align="center">
<div>

<Diagram
  fontSize={24}
  alt="getpid sequence: the program calls libc, which runs the syscall instruction; the kernel looks up the handler, runs it and returns to user mode."
  source={`sequenceDiagram
  participant P as Program
  participant L as libc
  participant K as Kernel
  P->>L: getpid()
  L->>K: syscall
  K->>K: sys_call_table
  K->>K: sys_getpid()
  K-->>P: sysretq`}
/>

</div>
<div>

<Reveal>

1. Prepare arguments
2. Pass control to the kernel
3. Validate arguments
4. Perform the operation
5. Return to user mode

</Reveal>

</div>
</Cols>

<Notes>

Syscalls cover process control like fork and exec, files, devices, system configuration, network and capabilities. Every one follows the same five steps.

**[→]** The program prepares the arguments; for `getpid` the libc wrapper puts the syscall number in a register. **[→]** It runs the special `syscall` instruction, which switches to kernel mode. **[→]** The kernel looks the number up in the syscall table and validates the arguments. This is where mediation happens. **[→]** It runs the handler, here `sys_getpid`. **[→]** And `sysretq` drops back to user mode.

Why does this matter? There is a limited number of entry points, so the attack surface is well defined. But the arguments are usually pointers into user memory, and handling them safely is entirely the kernel's job.

</Notes>
</Slide>

<Slide title="Processes">

## Processes

<Cols columns="1fr 1fr" gap={72} align="start">
<div>

<Reveal>

- A program **running**, with a **PID**. Root of the tree: `init`, PID&nbsp;1
- Users have a **UID** and **GID**. Root: UID&nbsp;0
- Children **inherit** privileges
- **IPC** only through syscalls: files, shared memory, pipes, sockets, signals

</Reveal>

</div>
<div>

<Step at={5}>

### Daemons

Background services: indexing, remote login, printing, file sync.

Start **before** the user, often with **more privilege**, and survive the session.

</Step>

</div>
</Cols>

<Notes>

**[→]** A process is a program loaded into memory with a process ID. The border between processes is a trust boundary, and the kernel gives each one CPU time, memory, and resources through syscalls. `pstree` shows the tree.

**[→]** Permissions depend on who created the process, through UIDs and GIDs. **[→]** Launching an app, the shell or GUI forks a new process, and descendants inherit their creator's privileges.

**[→]** Processes talk only through syscalls: files, shared memory, pipes and sockets, which are synchronous, and signals, which are asynchronous.

**[→]** Daemons are the processes you don't see. They start before you log in, often with more privilege than you, and outlive your session, so a bug in one is worth a lot.

</Notes>
</Slide>

<Slide title="Same user, no isolation">

## Same user, no isolation

<Cols columns="1fr 1fr" gap={72} align="start">
<div>

### Windows evolution

<Reveal>

- **DOS:** no memory protection
- **1.x to ME:** single-user, some user/kernel isolation
- **NT, 2000, XP:** multi-user, isolation **between users**, like Unix

</Reveal>

</div>
<div>

<Step at={4}>

### `/proc` on Unix

Processes appear as **files**.

`/proc/<pid>/mem` reads and writes another process's memory with plain `fopen`, `fread`, `fwrite`.

</Step>

</div>
</Cols>

<Notes>

The fundamental rule is that a process can't touch the memory of a process of a **different user**. Read that carefully.

**[→]** DOS had no memory protection at all; any program could write straight to screen memory. **[→]** Windows 1 to ME were single-user, with some separation between user space and kernel, and applications often ran as administrator. **[→]** From NT onward, Windows is multi-user and isolates users from each other, like Unix.

**[→]** But inside one user, processes are not isolated. On Unix, `/proc` shows every process as files and folders, and `/proc/<pid>/mem` lets you read and write another process's memory with normal file calls, as long as it's yours. `/proc/<pid>/stat` gives its statistics. Containers, later on, are the answer to this.

</Notes>
</Slide>

<Chapter title="Trust and boot" label="Systems Security 2">

<Slide title="Inductive trust">

## Trust by induction

<Reveal>

- **Base:** after a fresh install, BIOS, bootloader and kernel are trusted
- **Boot** loads the kernel and keeps that state
- The kernel starts processes that **cannot change it**
- **Hibernation** and admin **updates** must keep it too

</Reveal>

<Step at={5}>

<p class="lede">Trusted: does exactly, and only, what it was specified to do.</p>

</Step>

<Notes>

Trust in the OS works like a proof by induction. **[→]** The base case is a fresh install, which we trust by default. **[→]** Each boot step uses that trusted code to load the kernel and hand over control without breaking the trusted state. **[→]** The kernel launches processes with permissions that can't change it. **[→]** And anything that writes the state back, like hibernation, or an admin installing software, must preserve it.

The lecture's example of an update gap is the Blaster worm, 2003, on Windows 2000 and XP without SP2. A buffer overflow crashed a core service and shut the OS down, and it infected almost any unpatched machine on the Internet. Allegedly it came from reverse engineering the patch.

**[→]** "Trusted" means the system does exactly what it was specified to do: no data leaves without permission, it talks to the real Google, it encrypts the disk and clears memory at shutdown.

</Notes>
</Slide>

<Slide title="Anchoring trust in hardware">

## Anchoring the boot

<p class="lede">Threats: BIOS, hibernation files, bootloader, **cold boot**.</p>

<div class="cards" style="--n:3">
<div class="card" data-color="blue">

### TPM

Crypto chip that **stores** keys and credentials.

</div>
<div class="card" data-color="green">

### UEFI Secure Boot

Boots only firmware and OS **signed** by the board maker.

</div>
<div class="card" data-color="purple">

### OpenTitan

Open-source **root-of-trust** chip. Audit for backdoors, stop supply-chain attacks.

</div>
</div>

<Notes>

The boot anchors the trust model, so a bug there bypasses everything above. Cold boot attacks read RAM right after power-off; the lecture calls them a side channel.

The hardware answers. The TPM stores credentials and keys; it signs nothing for you. UEFI Secure Boot is a root of trust: it boots only components signed by the motherboard supplier. Google's OpenTitan, 2019, is open design for hardware: anyone can audit the chip for backdoors, and it proves cryptographically that nothing between BIOS and processor was modified.

The OS adds event logs, for example to spot a process crashing again and again under an exploit attempt, process monitors, and signed code installs. Still, most real problems are admin mistakes.

</Notes>
</Slide>

<Chapter title="Virtual memory" label="Systems Security 2">

<Slide title="Address translation">

## Virtual memory

<Reveal>

- Each process sees memory that **does not physically exist**: mediation
- Split into **4 KB pages**. Page table: sparse tree. Missing page: **page fault**
- The **TLB** caches translations and the **R/W/X** bits per page, like an ACL
- Caching, speculation and paging are fast, and also **attack vectors**

</Reveal>

<Notes>

The rule: no process reaches another user's memory, and the kernel is protected from user code. It's done by runtime mediation, hardware plus kernel.

**[→]** Address translation gives each process a limited view: isolation by complete mediation. **[→]** The space is bigger than RAM, so some pages live on disk, open to offline attacks unless the disk is encrypted. **[→]** Page tables in RAM are slow, so the TLB, the Translation Lookaside Buffer, caches recent translations with read, write and execute bits per page. X is the NX bit from the software chapter.

**[→]** The catch: these optimizations became attack vectors, Spectre and Meltdown, and the lecture links the cached pages to Dirty Pipe.

</Notes>
</Slide>

<Slide title="Kernel mapping">

## Kernel mapping

<Cols columns="1fr 1fr" gap={72} align="center">
<div>

<div class="layers"><span class="hot">Kernel: PR PW PX</span><span>Stack</span><span>Heap</span><span>Code: UR UX</span></div>

<p class="small muted">One process's address space.</p>

</div>
<div>

<Reveal>

- Kernel memory is **mapped into every process**, with **privileged** permissions
- A syscall needs **no page-table switch**
- Switching processes changes user tables, **never** the kernel's

</Reveal>

</div>
</Cols>

<Notes>

If the kernel and user address spaces were fully separate, every syscall would be a costly switch.

**[→]** So part of the kernel's virtual memory is mapped into each process, but with different permissions: privileged read, write and execute, not the user ones. The process can't touch it directly; it only reaches it through syscalls such as memory map. **[→]** On a syscall, the kernel memory is already there, and so is the part of the process that the syscall needs. **[→]** When the OS switches from one process to another, it swaps the user page tables but keeps the kernel's. So the kernel sits at the same place for everyone, and that's what Pegasus exploited, a few slides on.

</Notes>
</Slide>

<Slide title="Meltdown vs Spectre">

## Meltdown vs Spectre

<Cols columns="1fr 1fr" gap={72} align="start">
<div>

### Meltdown

<Step at={1}>

A **race** between the privilege check and the memory access.

</Step>

<Step at={2}>

Out-of-order execution reads and **caches** the data anyway. The access is rejected, but **timing** shows what's cached. Reads anything mapped in your process.

</Step>

</div>
<div>

### Spectre

<Step at={3}>

The attacker **trains** the CPU's branch prediction to guess wrong.

</Step>

<Step at={4}>

Other processes reuse the bad guess and touch memory the attacker picked. **Timing** reveals it.

</Step>

</div>
</Cols>

<Notes>

Both break process isolation and read data from running programs.

**[→]** Meltdown: the CPU checks privileges and accesses memory in parallel. **[→]** With out-of-order execution, the load lands in the cache before the check fails. The access is rejected, but cache timing reveals what was loaded. So the attacker reads any address mapped in its own process, and kernel memory is mapped in every process. Hence KPTI.

**[→]** Spectre: the attacker trains the speculative predictor to mispredict. **[→]** Another program reuses that wrong guess and speculatively touches locations the attacker chose, or runs injected speculative shellcode. Again, cache timing leaks it.

For the test: Meltdown is the privilege race in your own address space; Spectre tricks other programs through the predictor.

</Notes>
</Slide>

<Slide title="Dirty Pipe">

## Dirty Pipe (CVE-2022-0847)

<p class="lede">Overwrite **any file you can read**. A pipe-flag bug plus two optimizations: `splice()` and `PIPE_BUF_FLAG_CAN_MERGE`.</p>

<Reveal>

1. Open a file **read-only**
2. Create a pipe with the `CAN_MERGE` flag
3. Point the pipe at a section of the file
4. Write to the pipe: it overwrites the **cached page**

</Reveal>

<Notes>

Dirty Pipe, 2022, in the Linux kernel. Three ingredients: a bug that lets you create pipes with arbitrary flags; `splice()`, which quickly pushes a file's contents into a pipe without copying; and `CAN_MERGE`, which lets the kernel update a "dirty" page without rewriting the data.

**[→]** You open, say, `/etc/passwd` read-only. **[→]** You make a pipe that carries the merge flag. **[→]** You splice the file into it, so the pipe now points at the file's page in the page cache. **[→]** Anything you write to the pipe lands in that cached page, so every reader sees your version. Read permission became write permission. We'll see the mitigation in the last lecture.

</Notes>
</Slide>

<Slide title="Pegasus">

## Pegasus: the iOS kernel (2016)

<p class="lede">`OSUnserializeBinary` did not sanitize **syscall arguments**: elements with no closing tag, wrong sizes.</p>

<Reveal>

1. **CVE-2016-4655:** an overflow leaks the kernel's **location**
2. **CVE-2016-4656:** casting bad objects gives a **use-after-free**
3. Many threads, so no one else **reuses** the freed memory
4. Shellcode through **ROP**: jailbreak

</Reveal>

<Notes>

Pegasus, the NSO spyware, chained iOS kernel bugs in a function that unpacks serialized syscall data. Think of XML with missing closing tags and lying sizes.

**[→]** Reading the malformed input overflows into sensitive kernel memory, so the attacker learns where the kernel lives. With kernel mapping, it's at the same place in every process, so one leak is enough. **[→]** Second, the kernel casts the malformed objects in a way that leaves a dangling pointer: a use-after-free. **[→]** The attacker spawns many threads so other processes are unlikely to grab that freed memory first. **[→]** And then injects shellcode with ROP, from the software chapter, which ends in a jailbreak. The lecture slide prints 4655 for both bugs; the corruption one is 4656.

</Notes>
</Slide>

<Slide title="Protecting the kernel">

## Defense in depth for the kernel

<Reveal>

- The kernel with **all** permissions on user memory? No
- Not even the kernel may break **W^X**
- The kernel should not **write** user memory: stops leaks and code injection
- **KPTI:** page tables (almost) **fully separate**. Cost ~5%, up to 30%

</Reveal>

<Notes>

The question is what permissions the kernel should have on user memory. **[→]** "All of them" is the wrong answer, because we want protection even against a corrupted kernel.

**[→]** So W xor X applies to the kernel too: no page both writable and executable. **[→]** And the kernel is blocked from writing to user regions, which protects against information leaks and against the kernel running attacker code placed in user memory. The 2021/22 test asked for one such limit and the principle behind it: this is the answer, and the principle is defense in depth.

**[→]** KPTI, Kernel Page-Table Isolation, removes almost all of the kernel from the user page tables, which kills Meltdown. The price is performance, about 5%, up to 30% for syscall-heavy loads.

</Notes>
</Slide>

</Chapter>

<Slide title="Unix permissions">

## Unix permissions

<Cols columns="1fr 1fr" gap={72} align="start">
<div>

| | file | folder |
| --- | --- | --- |
| `r` | read | list contents |
| `w` | write | create contents |
| `x` | execute | enter |

</div>
<div>

<p class="big"><code style="font-variant-ligatures: none">-rwxrw-r--</code></p>

<Reveal>

- First character: type (`-` file, `d` folder)
- Then **owner**, **group**, **others**
- Groups give a kind of **RBAC**

</Reveal>

</div>
</Cols>

<Notes>

We use Unix as the example. Actors are users and processes, resources are files and folders.

On files, r, w and x mean what you expect. On folders they change: r lists the contents, w creates new contents, and x lets you enter the folder. A test trap: x on a folder is not "execute".

**[→]** The first character of `ls -l` is the type. **[→]** Then three triplets: owner, group, everyone else. Each resource has an owner and a group, and permissions are given to each independently. **[→]** Because users belong to groups and groups get permissions, the group column is role-based access control in miniature.

</Notes>
</Slide>

<Slide title="Extended ACLs">

## Extended ACLs and the mask

```text {2,7}
$ ls -l myfile
-rw-r-----+ ... tux linux ... myfile
$ getfacl myfile
user::rw-
group::r-x            # effective:r--
group:penguins:r-x    # effective:r--
mask::r--
other::---
```

<Step at={1}>

<p class="big">Effective = entry **and** mask.</p>

<p class="big"><code>setfacl -m u:nobody:rw myfile</code></p>

</Step>

<Notes>

Many Unix file systems also support extended ACLs, which add named users and named groups beyond owner, group and other. The `+` at the end of the permissions is how `ls` tells you one exists.

Read the `getfacl` output. The owning group and the group "penguins" both have r-x, but the mask is r--, so their effective permission is only r--.

**[→]** The mask is the maximum permission for every named user and group, and for the owning group. It exists for applications that don't understand ACLs. And `setfacl -m` modifies the ACL, here giving the user nobody read and write.

</Notes>
</Slide>

<Slide title="Who can change what">

## Who can change what

<Cols columns="1fr 1fr" gap={72} align="start">
<div>

### Superuser

UID 0. Once a user (**root**), now a role (**sudo**). Use it as little as possible.

<Reveal>

- `chown`: superuser only
- `chgrp`: owner or superuser
- `chmod`: owner or superuser

</Reveal>

</div>
<div>

<Step at={4}>

### DAC vs MAC

**Discretionary:** the owner sets permissions.

**Mandatory:** only the superuser or a system policy, e.g. **SELinux**.

</Step>

</div>
</Cols>

<Notes>

The superuser can do everything. It used to be a special user called root; today it's more of a role you take with sudo. Least privilege says use it as little as you can.

**[→]** Changing the owner, chown, is for the superuser only. Otherwise you could give your files to someone else to dodge quotas or plant files on them. **[→]** Changing the group, chgrp, the owner or the superuser. **[→]** Changing the permissions, chmod, also the owner or the superuser.

**[→]** That last fact is what makes the Unix file system discretionary access control, DAC: the owner decides at their discretion. In mandatory access control, MAC, users can't, only the superuser or a central policy, like SELinux. The 2021/22 test asked exactly this: why is Unix DAC, and what makes MAC different.

</Notes>
</Slide>

<Slide title="Login and the setuid bit">

## Login and the setuid bit

<Flow
  items={[
    "login|runs as root",
    "authenticate|reads credentials",
    "drop privileges|uid, gid := user",
    "shell|as the user",
  ]}
  highlight={[2]}
/>

<Step at={1}>

<p class="lede">**setuid bit:** the process runs as the file's **owner**, not as you. `passwd` is owned by root.</p>

</Step>

<Step at={2}>

<p class="big">**CVEs:** `passwd` (2004-0360), `sudoedit` (2023-22809)</p>

</Step>

<Notes>

Every process has an effective user ID that decides its permissions, usually the launcher's. Exceptions: sudo and passwd.

Login runs as root so it can read the stored credentials, authenticates you, changes its UID and GID to yours, and launches your shell. The critical step is dropping privileges. Done wrong, the process keeps something it got as root, like an open file: capability leaking.

**[→]** Escalating should be impossible, yet passwd must edit a root-owned file for you. The setuid bit makes the process run with the UID of the executable's owner; the superuser or the owner can set it. If the owner is root, any bug is a privilege escalation.

**[→]** Two real ones: a buffer overflow in passwd on Solaris in 2004, and sudoedit in 2023, where extra arguments in an editor environment variable let a user edit arbitrary files as root.

</Notes>
</Slide>

<Slide title="Three UIDs">

## Three UIDs per process

<div class="cards" style="--n:3">
<div class="card" data-color="blue">

### EUID

*effective*: **permissions**.

</div>
<div class="card" data-color="green">

### RUID

*real*: who **launched** it.

</div>
<div class="card" data-color="orange">

### SUID

*saved*: the **previous** user, for transitions.

</div>
</div>

<Step at={1}>

<p class="big"><code>setuid(x)</code> as root: all three := x. **Permanent.**</p>

</Step>

<Step at={2}>

<p class="big"><code>seteuid(x)</code>: only the EUID. **Temporary.**</p>

</Step>

<Notes>

Normal processes run with the launcher's UID, setuid ones with the owner's, kernel processes as UID 0, maximum privilege. The transitions are subtle, so each process has three UIDs.

**[→]** Root can call `setuid(x)` and set all three to anything. A normal user can only set the EUID to the RUID, themselves, or the SUID, going back. That's how a process drops privileges for good: Apache runs as root to open port 80, then forks workers that drop to a normal user.

**[→]** `seteuid(x)` changes only the EUID and keeps RUID and SUID. That's a temporary drop: lower, run some code, restore. The danger is using `seteuid` when you meant to drop for good: the saved root lets the process climb back. That mistake is CVE-2000-0525.

</Notes>
</Slide>

<Slide title="setuid and the environment">

## setuid programs and the environment

<Cols columns="1fr 1fr" gap={72} align="start">
<div>

### `system(cmd)`

Runs `/bin/sh -c cmd` with the **caller's environment**. The shell parses `;` and searches `PATH`.

</div>
<div>

### `execve(path, argv, envp)`

Runs the program **directly**. No shell. The environment is whatever you pass.

</div>
</Cols>

<Reveal>

- `PATH`: a relative `ls` may run **your** `ls`
- `LD_PRELOAD`: replaces **shared library** functions only
- Defenses: the loader ignores `LD_PRELOAD` in setuid processes; the shell may drop privileges

</Reveal>

<Notes>

This is from the Environment Variable and Set-UID lab, and tests ask about it almost every year.

`system` forks and runs `/bin/sh -c` with your command, and the shell inherits the program's environment, interprets characters like the semicolon, and finds bare names through `PATH`. `execve` runs exactly the binary you name with the arguments and environment you give. No shell.

**[→]** In a setuid program, `system("ls")` trusts `PATH`, and you control `PATH`. Put your own `ls` first and it runs with the program's privileges. **[→]** `LD_PRELOAD` loads your library first, so you can replace dynamically linked functions like `printf` or `malloc`. Functions defined inside the program itself are not affected. **[→]** Both are so dangerous that the dynamic loader ignores `LD_PRELOAD` when EUID and RUID differ, and shells like dash drop privileges when they detect they run setuid. So a child may get the environment minus some critical variables.

</Notes>
</Slide>

### Android

</Cols>

<Notes>

How do you keep the number of syscalls, and the attack surface, small? Use the same interface for files and everything else. On Unix, sockets, pipes, I/O devices and kernel objects all look like files, so the same access control checks them all.

**[→]** Android reuses the user mechanism in a clever way: each app gets its own Linux user, so apps are isolated like different people. On top it runs SELinux, so it's mandatory access control. The problem is multiple real people on one tablet. The ad hoc fix is IDs like `u1_a23`: user 1, app 23. And each app declares permissions in its manifest.

</Notes>
</Slide>

## LSM: one more layer over DAC

<Flow
  items={[
    "Syscall",
    "Check errors",
    "DAC",
    "LSM hook",
    "Resource",
  ]}
  highlight={[3]}
/>

<Reveal>

- Since kernel 2.6, models load as **kernel modules**
- Any step that fails **denies**: LSM can only **add** restrictions
- A truly **generic reference monitor**

</Reveal>

<Notes>

Linux Security Modules let you load access control models into the kernel, on top of normal DAC.

The order of checks: the syscall arrives, the kernel checks the arguments, then the normal Unix permissions, then the LSM hook, where SELinux or AppArmor ask their policy, and only then the resource.

**[→]** They are loadable kernel modules, since 2.6. **[→]** Because every step must pass, an LSM can only take permissions away, never grant more. **[→]** That's why the lecture calls it a truly generic reference monitor: one place where any policy can mediate.

</Notes>

<Slide title="Unix: the verdict">

## Unix access control: the verdict

<p class="lede">ACLs with some batching (RBAC). **Simple**, and works in practice.</p>

<Reveal>

- A bug in `passwd` or `ssh` (EUID 0) is **catastrophic**
- Root is used, often wrongly, for **too much**
- Once an attacker has root, you **can't** downgrade them
- Trust transitions are easy to get wrong: **log** them

</Reveal>

<Notes>

The lecture's summary. Unix access control is basically access control lists with grouping, so RBAC. Without extended ACLs and LSM it's simple and it works.

But it's not robust or flexible. **[→]** Programs that run as EUID 0 and parse user input are single points of failure. **[→]** Root does many unrelated jobs, which leads to admin mistakes. **[→]** There is nothing above root, so once an attacker has it, you can't take it back. **[→]** And even this simple system has transitions between trust states that are easy to get wrong, so compromise recording matters.

</Notes>

## Confining untrusted code

<p class="lede">JavaScript, extensions, legacy code, honeypots, malware analysis. If it misbehaves, **kill it**.</p>

<Reveal>

- **Air gap:** separate hardware. Hard to manage
- **Processes:** a virtual view per process. Weak against same user, admin, OS bugs
- **VMs:** a hypervisor shares hardware between OSes
- **Sandbox:** inside an app, e.g. JavaScript and WebAssembly
- **Containers:** share the host **kernel**, isolate userland

</Reveal>

<Notes>

We often run untrusted code on a trusted platform. If it misbehaves, nuke it.

**[→]** The strongest level is physical, an air gap, and a pain to manage. **[→]** Next, the OS gives each process a virtual view, so P1 can't affect P2. Weak spots: same-user processes, admin processes, OS bugs. On Unix this rests on SFI and SCI, the next question. **[→]** VMs: the hypervisor gives each OS a virtual view of the hardware. **[→]** Sandboxing confines inside one app, like a browser's JavaScript and WebAssembly interpreters. **[→]** Containers: a VM runs a whole OS, more isolation; a container shares the host kernel, fewer resources.

</Notes>

## chroot (1979)

<Cols columns="1fr 1fr" gap={72} align="center">
<div>

<Reveal>

<Slide title="Escaping chroot">

## Escaping a chroot jail

<Reveal>

- **Early versions:** `fopen("../../etc/passwd")` just walks out
- **Ultrix 4.0:** a non-root user could run `chroot`
- Root inside the jail: create a **raw disk device**, **signal** outside processes, **reboot**

</Reveal>

<Step at={2}>

<Flow

</Step>

**[→]** At first, relative paths escaped: `/tmp/guest/../../etc/passwd` resolved outside the jail.

**[→]** Ultrix 4.0 let a non-root user run chroot. So you write your own password file in `/aaa/etc/passwd`, with a root entry whose password you know, then chroot into `/aaa`. When you type `su root`, which password file does su read? Yours. You are root. That's why chroot is root-only.

**[→]** And the general rule: the user inside a jail must never become root, because root has many ways out. It can create a device file for the raw disk and read anything, send signals to processes outside, or simply reboot the machine.

</Notes>

Recap: the kernel now offers namespaces, cgroups and limits on root, all mediation.

<Slide title="System call interposition">

## System call interposition

<p class="lede">The attack surface is the **syscalls**. Watch them and block the unauthorized ones.</p>

<Cols columns="1fr 1fr" gap={72} align="start">
<div>

<Reveal>

- **In the kernel:** seccomp
- **In user space:** program shepherding
- **Hybrid:** Systrace

</Reveal>

</div>
<div>

<Step at={4}>

### Chromium sandbox

1. **SFI:** no files, network or other processes
2. **SCI:** restrict the syscalls, the main attack surface

</Step>

</div>
</Cols>

<Notes>

To change the real system, code must go through the file system or the network, and both are syscalls. So SCI monitors syscalls and blocks the ones that aren't allowed. That's complete mediation.

**[→]** You can do it inside the kernel, like seccomp in Linux, **[→]** outside the kernel in user space, which is called program shepherding, **[→]** or a mix of both, like Systrace.

**[→]** Chromium is the example of defense in depth: layer one, SFI, keeps the renderer away from files, network and other processes; layer two, SCI, restricts the syscall interface itself.

</Notes>
</Slide>

## The first try: ptrace

<Cols columns="1fr 1.3fr" gap={56} align="center">
<div>

<Step at={1}>

Slow, duplicated on forks, abort = kill. And **TOCTOU**: check and use are not atomic.

</Step>

</div>
<div>

<Step at={1}>

<Diagram
  fontSize={24}

On Linux, `ptrace` lets a monitor attach to a child process and get notified whenever it makes a syscall. If the call isn't allowed, the monitor kills it. The Janus system used this for policies like "allow `/tmp/*`, deny `/etc/passwd`, deny all network".

**[→]** The limits: it intercepts every call, so it's slow. The monitor has to be duplicated on every fork. Aborting one syscall means aborting the whole process. And the worst: TOCTOU, time of check to time of use. Process 1 asks to open "me". The monitor checks and says OK. Before the kernel runs it, process 2 replaces "me" with a symlink to `/etc/passwd`. The open runs and gets the wrong file. Checking and running are not one atomic step.

</Notes>

<Slide title="seccomp">

## seccomp

<Cols columns="1fr 1.3fr" gap={64} align="start">
<div>

### Strict mode

After `prctl()`: only exit, return and **already open** files. Violation: the kernel **kills** it.

</div>
<div>

### seccomp-bpf

<Reveal>

- Fine-grained **BPF** rules: syscall, arguments, architecture
- Returns `KILL`, `ERRNO` or `ALLOW`
- Filters can't be **removed**, and pass to **all descendants**
- **Immune to TOCTOU**
- Used by Chromium and Docker

</Reveal>

</div>
</Cols>

<Notes>

Secure Computing Mode puts SCI inside the kernel. In strict mode, the process calls `prctl()` and from then on can only terminate, return, or use files it already had open. No new files, no fork. Anything else and the kernel kills it.

seccomp plus BPF makes it configurable with Berkeley Packet Filter rules. **[→]** A rule looks at the syscall number, its arguments and the architecture. **[→]** The kernel runs the filter on every syscall and returns kill the process, reject with an error, or allow. **[→]** A process can install several filters; once installed they can't be removed or turned off, and every descendant inherits them, even across `execve`. **[→]** It's in the kernel, so there's no gap between check and use. **[→]** Chrome forks its renderer and installs the policy with `prctl`. If an exploited renderer calls `fopen("/etc/passwd")`, seccomp-bpf kills it.

</Notes>
</Slide>

<Slide title="Docker and seccomp">

## Docker and kernel mitigations

<Cols columns="1fr 1fr" gap={72} align="start">
<div>

### Docker

Containers are **child processes** of the engine. The default seccomp profile **blocks many syscalls**, `ptrace` included.

`--security-opt seccomp=profile.json`

</div>
<div>

<Step at={1}>

### Until you patch

**Dirty COW:** block `ptrace()` and writes to `/proc/self/mem`.

**Dirty Pipe:** block `splice()`.

</Step>

</div>
</Cols>

<Notes>

Docker uses seccomp-bpf the same way. The containers are sub-processes of the Docker engine, so the engine filters their syscalls. The default policy blocks many calls, including ptrace, and you can change it with a JSON profile.

**[→]** The same idea mitigates kernel bugs. Two famous CVEs let you overwrite read-only files. Dirty COW, 2016, is a race in copy-on-write, a feature there to support debuggers, attacked through `ptrace()` or `/proc/self/mem`. Dirty Pipe is the zero-copy optimization we saw, attacked through `splice()`. Until the kernel is updated, you block those syscalls and limit capabilities or access to certain files.

</Notes>
</Slide>

## eBPF (2014)

<Slide title="Software fault isolation">

## Software fault isolation

<p class="lede">Sandboxing with minimal overhead: each app gets a **memory segment** and may only access it.</p>

<Reveal>

- **Guards** before dangerous instructions, by binary instrumentation or at compile time
- Dangerous: **loads and stores**, and **jumps**
- Hard on **x86**. Alternative: separate address spaces, with **IPC** cost

</Reveal>

<Notes>

SFI is least privilege for memory. Each application gets its own segment, and the code is controlled so every access stays inside.

**[→]** Every dangerous operation gets a guard before it: check the segment, or force the address into it. You add guards by instrumenting the binary, or at compile time, as the CompCert work does. **[→]** Loads and stores are obvious. Why jumps? Because a jump could land past a guard, or in code that has none, and run unchecked instructions. So jump targets are validated too. **[→]** On x86 this is hard: many registers and many dangerous instructions. The other way to isolate is separate address spaces, but then every call between them costs inter-process communication.

</Notes>
</Slide>

<Slide title="Google NaCl">

## Google Native Client

<Reveal>

- Native C/C++ in Chrome, e.g. games. **POSIX**: files, sockets, threads
- Compiled **ahead of time**: much faster than JIT JavaScript
- **SFI + CFI**. Overhead 5% on ARM, 7% on x86-64
- Dropped in 2016 for **WebAssembly**

</Reveal>

<Notes>

NaCl is the SFI example. **[→]** It was a sandbox to run native code in the browser, a pioneer in moving C and C++ libraries to the web; they even ran Doom. **[→]** Code compiled ahead of time is much faster than JavaScript compiled just in time. **[→]** It combined software fault isolation for memory with control-flow integrity for jumps, which is exactly the jump problem from the last slide, and cost only 5 to 7%. **[→]** Google discontinued it in 2016; today C and C++ compile through LLVM to WebAssembly.

</Notes>
</Slide>

## Virtual machines

<Cols columns="1fr 1fr" gap={72} align="start">
<div>

### Why they work

- A hypervisor is **simpler** than an OS

<Slide title="Red Pill vs Blue Pill">

## Breaking isolation

<Cols columns="1fr 1fr" gap={72} align="start">
<div>

### Side channels

Delays in memory access, cache effects. CPUs **can't** guarantee full isolation: Meltdown, Spectre.

<Step at={1}>

### Red Pill: am I in a VM?

Instructions, hardware, memory latency, small resources. Hypervisors give compatibility and performance, **never transparency**.

</Step>

</div>
<div>

<Step at={2}>

### Why care?

Malware **hides** from analysis. Vendors **demand** real hardware. DRM.

</Step>

<Step at={3}>

### Blue Pill

A rootkit that moves your running OS **into the attacker's VM**.

</Step>

</div>
</Cols>

<Notes>

Side channels observe side effects, like cache traces one process leaves for another to measure. Modern CPUs share too much hardware to promise full isolation.

**[→]** Red Pill: can a program tell it's in a VM? Yes: available instructions, hardware features, memory latency, limited resources. Websites do it too: crawlers in VMs hunt for sites that inject malware, so those sites measure screen rendering latency and behave when watched. Hypervisors offer compatibility and performance, but not transparency. An "archaic" instruction set with 8 GB of RAM gives it away.

**[→]** Why it matters: malware is analyzed in VMs, so it wants to detect them and play dead. Software makers may demand real hardware or a hardware key, and so may DRM.

**[→]** Blue Pill, by Joanna Rutkowska, who founded Qubes, reverses the roles: a rootkit that slides a hypervisor under the running OS. The OS becomes the guest and can't see the attacker's layer.

</Notes>
</Slide>
