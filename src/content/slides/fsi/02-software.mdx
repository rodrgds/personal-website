## Software can turn against us

<Flow items={["Weakness|in the process", "Vulnerability|a specific error", "Exploit|a concrete way in", "Attack"]} />

<Reveal start={1}>

- Mallory sends **input from outside the security perimeter**
- Goal: break **control-flow integrity** and run her code
- Stealing control = **write** malicious instructions, then **execute** them

</Reveal>

<Notes>

Software runs on a platform: memory, disk, the OS, the hardware. Every program is a potential weapon against that platform. Alice is the honest user, Mallory exploits a bug in the program, the OS or the hardware.

The chain from the lecture: weaknesses in development lead to vulnerabilities, specific errors that can cause damage. An exploit is a concrete way to cause that damage, and an attack is using it. We study old attacks because knowing about a flaw and not fixing it is negligence.

**[→]** The threat model for this whole part: the program receives input from outside the security perimeter. Mallory controls those bytes. **[→]** Is crashing Word a vulnerability? Yes, a crash is already a denial of service. But the real prize is control: most of these bugs let the attacker change the control flow of the program. **[→]** And stealing control always takes two steps: get malicious instructions into memory, then get the program to jump to them.

</Notes>
</Slide>

<Notes>

Now a function call. `main` calls `f(1, 2)`, and `f` has a 16-byte buffer. Two registers matter: `esp`, the stack pointer, marks the end of the stack, and `ebp`, the frame pointer, marks the start of the current frame.

**[→]** The caller pushes the arguments, last to first, so `b` ends up above `a`.

**[→]** The `call` instruction pushes the return address: where to continue when `f` ends.

**[→]** Inside `f`, the old `ebp` is saved and `ebp` now points here.

**[→]** Then `esp` moves down to make room for the locals.

**[→]** Look at the order from top to bottom: arguments, return address, saved ebp, buffer. The buffer is **below** the return address, and copies write **upward**. You can see where this is going. When `f` returns it cleans its locals, `ret` pops the return address, and the caller cleans the arguments. That last detail matters later for ROP.

</Notes>

## Stack smashing

<Cols columns="1fr 1000px" gap={64} align="start">
<div>

```c
void f(char *str) {
  char buf[128];
  strcpy(buf, str);
}
```

<Reveal start={1}>

- `strcpy` copies **up to the `\0`**, ignoring the size of `buf`
- If `str` comes from **outside the perimeter**, the attacker picks the bytes
- Root cause: **no separation between code and data**

</Reveal>

</div>

<Notes>

The classic attack. `f` has a 128-byte buffer and copies a string that comes from outside.

**[→]** `strcpy` copies until it finds a zero byte. It doesn't know the size of the destination. If the string is longer than 128 bytes, the copy fills the buffer and keeps going upward.

**[→]** If that string crosses the security perimeter, the attacker chooses every byte. **[→]** And the deeper problem: on the stack, the return address, which decides where the program goes next, sits right next to attacker data. Code pointers and data share the same memory.

The copy goes on: **[→]** over the saved ebp, **[→]** and over the return address. When `f` returns, it jumps to 0x41414141, which is "AAAA". Crash.

But the attacker wants control, not a crash. **[→]** So she puts machine code in the buffer and writes the buffer's address over the return address. Now `ret` jumps into her code. That's stack smashing.

</Notes>
</Slide>

<Notes>

Let's watch it happen. This is a simulation with the real rules: a 16-byte buffer, little-endian, and `strcpy` always writes a `\0` at the end. Each row is a 4-byte word, addresses growing upward.

"rodrigo" is fine: 7 bytes plus the zero.

**[→]** 15 A's: 15 bytes plus `\0` is exactly 16. Still fits.

**[→]** 16 A's: now the `\0` lands on the first byte of the saved ebp. One byte too many. That's the off-by-one, or poisoned NUL byte: the caller's frame pointer now points somewhere else, and when the caller returns it reads its return address from a place the attacker controls. So one byte can be enough.

**[→]** 16 A's, BBBB and CCCC. BBBB goes into the saved ebp, CCCC into the return address: 0x43434343. On return, it jumps there and crashes.

**[→]** Now for real: NOPs, 0x90, then shellcode bytes, BBBB for the ebp, and at the end the buffer's own address, written backwards because of little-endian. The return address points into the buffer, so the CPU runs our input.

If you're watching on the site, type into the box yourself. Use `\x41` to enter raw bytes.

</Notes>
</Slide>

## Shellcode and NOP sled

<Cols columns="1fr 960px" gap={64} align="start">
<div>

<Reveal class="small">

- **Shellcode**: machine code that opens a shell
- The buffer address **varies**: put a **NOP sled** (0x90) in front. Landing on any NOP works.
- **No `\0`** in the payload: `strcpy` would stop at the first zero byte
- More robust: shellcode **above** the ret, ret pointing to a `jmp esp`

</Reveal>

</div>
<div>

<Notes>

What code do we inject? Shellcode: assembly that runs shell commands, usually `execve` of "/bin/sh". It's the holy grail of remote code execution.

**[→]** The catch: the attacker doesn't know the exact buffer address, because it changes with the environment variables and the platform. **[→]** So in front of the shellcode she puts a NOP sled. If the return lands anywhere on it, **[→]** the CPU executes NOPs, which only advance the program counter, **[→]** until it reaches the shellcode. The bigger the sled, the worse the guess can be.

The payload must not contain a zero byte, because `strcpy` stops copying at the first `\0` and the rest never arrives. That's the answer to the 2021 open question: 0x90 helps, 0x00 breaks the copy.

And a trick from the lecture: put the shellcode right above the return address and point the return address at an existing `jmp esp` instruction. Then you don't guess any address.

</Notes>
</Slide>

## 1988: the Morris worm

<Cols columns="1fr 1fr" gap={72}>
<div>

```c
// fingerd
char line[512];
// ...
gets(line);
```

<Step at={1}>

`gets` reads **whatever** the client sends. 536 characters reach the return address.

</Step>

<Step at={2}>

<p class="small muted">1972 concept documented · 1988 Morris worm · 1996 "Smashing the Stack for Fun and Profit" · console jailbreaks</p>

</Step>

</div>
<div>

<Step at={3}>

| function | problem |
| --- | --- |
| `strcpy`, `strcat` | no size check |
| `gets`, `scanf("%s")` | read as much as the input sends |
| `strncpy` | bounded, but **may skip the `\0`** |

</Step>

<Step at={4}>

<p class="small">And hand-written code that <strong>assumes trusted input</strong>: libpng 2004, realpath off-by-one 2003, poisoned NUL byte 1998 and 2014.</p>

</Step>

</div>
</Cols>

<Notes>

The first documented hostile use of a buffer overflow was the Morris worm, 1988. It had no payload, it just spread itself. Its author went from Cornell student to convicted felon to MIT professor.

**[→]** The bug was in `fingerd`: a 512-byte buffer and `gets`, which reads everything the client sends. 536 characters were enough to overwrite the return address.

**[→]** Some history: the concept was documented in 1972. In 1996 Aleph One published "Smashing the Stack for Fun and Profit", which made the technique common knowledge. It's also how many Wii, PS2 and Xbox jailbreaks worked.

**[→]** Why so common? libc string functions that don't know the destination size: `strcpy`, `strcat`, `gets`, `scanf`. And watch `strncpy`: it limits the length, but if the source is too long it doesn't write the `\0`. Classic trap.

**[→]** And hand-written code that assumes input is trusted. libpng in 2004 lacked input validation, realpath had an off-by-one in 2003, and the poisoned NUL byte from the demo was exploited in 1998 and again in 2014.

</Notes>
</Slide>

<Slide title="Why not safe languages">


## Why not just use safe languages?

<Reveal>

- Safe languages **compile to** or **call** C / LLVM libraries
- VMs, browsers and OSes are written in **low-level languages**
- Cryptographic code is **optimized by hand**
- Attacks **chain** several vulnerabilities
- Input is **always** potentially malicious

</Reveal>

<Step at={6}>

<p class="big">2023 <strong>CWE Top 25</strong>: #1 out-of-bounds write, #4 use-after-free, #7 out-of-bounds read.</p>

</Step>

<Notes>

Fair question: if C is this dangerous, why not use Java, Python, Rust?

**[→]** Because those languages often compile to C or call C and LLVM libraries underneath. **[→]** Because the virtual machines, sandboxes, browsers and operating systems they run on are still written in low-level languages. **[→]** Because in fields like cryptography, humans still optimize code better than compilers. **[→]** Because attacks chain vulnerabilities, so one unsafe piece is enough. **[→]** And because input is always potentially malicious, whatever the language.

**[→]** And it's not old news: in the 2023 CWE Top 25, memory errors hold three places.

</Notes>

## Heap overflow

<Cols columns="1fr 960px" gap={64} align="start">
<div>

```c
char *b1 = malloc(40);
char *b2 = malloc(40);
gets(b1);   // > 40 bytes
free(b1);
exit(0);
```

<Reveal start={3} class="small">

- Targets: **function pointers**: C++ vtables, GOT, exception handlers, longjmp buffers
- **Harder** than the stack: the layout varies

</Reveal>

</div>
<div>

  captions={[

    { at: "2", text: "free unlinks and writes through those pointers: exit() now points to the shellcode." },

</div>

<Notes>

On the heap the bug is the same: a block of 40 bytes and `gets` writing more into it.

But there's no return address on the heap. What's there instead? Each malloc chunk has control data: `prev_size`, `size`, and when it's free, two pointers, `fd` and `bk`, that link it into the free list.

**[→]** The overflow of `b1` runs into the header of the next chunk. **[→]** When `free` runs, the allocator checks whether the neighbor is free and merges them. Merging unlinks a chunk from the list, which writes through `fd` and `bk`. The attacker controls both, so she controls one write to memory: for example, replacing the address of `exit()` with the address of her shellcode. Then the program calls `exit` and runs her code. That's "smashing the heap".

**[→]** Other targets: the heap is full of function pointers. A C++ object stores a pointer to its vtable, so `obj->foo()` is an indirect call. Dynamic libraries go through the global offset table. Exception handlers and `longjmp` buffers are also code addresses.

**[→]** It's harder than the stack, because C only promises contiguous blocks. Where they land depends on the allocator, the OS and the hardware. To build an exploit you must predict the address you want to take over, predict where the shellcode will be, and avoid crashing first.

</Notes>
</Slide>

## Integer overflow

<Cols columns="1fr 1fr" gap={72} align="start">
<div>

<Reveal>

- **Truncation**: `int` 0x12345678 into a `short` keeps 0x5678
- **Bounded arithmetic**: 8-bit 0xff + 1 = 0, so `malloc(0)`
- **Sign**: 0xffffffff is −1 signed, 4,294,967,295 unsigned
- **Mixed widths**: 16-bit vs 64-bit

</Reveal>

</div>
<div>

<Step at={4}>

```c
unsigned short len = strlen(s);
char buffer[100];
if (len < sizeof buffer)
  strcpy(buffer, s);
```

</Step>

</div>
</Cols>

<Notes>

Integer overflow: the machine's fixed-size integers lose information. Arithmetic is modulo 2 to the n.

**[→]** Truncation: casting to a smaller type drops the high bytes. **[→]** Bounded arithmetic: in 8 bits, 0xff plus 1 is 0. If that's a size, you allocate 0 bytes instead of 256. **[→]** Sign: the same 32 bits are minus 1 or about 4 billion. A check like `x < 100` passes for minus 1, and then `x` is used as a huge unsigned size.

**[→]** Mixed widths, from the lecture: the length is stored in an `unsigned short`, 16 bits, but `strlen` returns a 64-bit `size_t`. A string of 65,536 plus 50 characters is stored as length 50. The check `len < 100` passes, and `strcpy` copies the whole 65 KB into a 100-byte buffer.

</Notes>

## Injecting code got harder

<div class="cards">
<div class="card" data-color="blue">

### DEP / W^X

A page is **writable or executable**, never both. Shellcode on the stack no longer runs.

</div>
<div class="card" data-color="green">

### ASLR

Addresses are **shuffled** on each run. You no longer know where the buffer is.

</div>
<div class="card" data-color="orange">

### JIT spraying

Constants compiled by the JIT are valid instructions if you jump mid-way. JIT code is executable (beats DEP) and sprayed (beats ASLR).

</div>
</div>

<Step at={1}>

<p class="big"><strong>Code reuse</strong>: use what is already executable. libc has <code>system()</code> and <code>mprotect()</code>.</p>

</Step>

<Notes>

Modern OSes make both steps of stealing control harder.

DEP, or W^X, write xor execute: a page can be written or executed, never both. The stack is writable, so it's not executable, and shellcode there won't run. The exception is just-in-time compilers.

ASLR: the locations of the stack, heap, libraries and code are shuffled on each run.

JIT spraying abuses that exception. Java, JavaScript and Flash compile hot code to machine code on the fly. The attacker writes harmless-looking code full of constants. The JIT turns each constant into bytes inside instructions. Jump into the middle of an instruction, a "half address", and those bytes decode as the attacker's instructions. That code is executable, so DEP doesn't help, and the attacker can make the JIT produce many copies, so ASLR doesn't help.

**[→]** The general idea, though: if you can't inject code, reuse code that's already in executable memory. Linked libraries. Chrome uses around a hundred, and almost every program links libc, which has `system` to run a shell command and `mprotect` to change memory permissions. Library addresses are also easier to predict.

</Notes>
</Slide>

## Chaining returns

<Cols columns="1.3fr 1fr" gap={72} align="start">
<div>

<MemoryStack
  width={1000}
  rows={[
    { value: "…", tone: "muted" },
    { value: "&f3", tone: "gadget", focus: "3" },
    { value: "&f2", tone: "gadget", focus: "2-2" },
    { value: "&f1", tone: "gadget", label: "the overwritten ret", focus: "1-1" },
  ]}
  pointers={[
    { name: "esp", row: 3, at: "1-1" },
    { name: "esp", row: 2, at: "2-2" },
    { name: "esp", row: 1, at: "3" },
  ]}
/>

</div>
<div>

<Reveal start={1}>

- Each `ret` pops the **next** address
- First function = **lowest** address
- Only the **last** one takes arguments easily

</Reveal>

</div>
</Cols>

<Notes>

If one libc function works, why not N in a row? That's return-oriented programming. Start with the simple case.

**[→]** A function with no parameters only uses its return address, and `ret` always removes it. So the overwritten return address is `&f1`: `f1` runs, and when it returns it pops the next word. **[→]** That's `&f2`. **[→]** Then `&f3`. The functions go in the stack in reverse order: the first to run at the lowest address.

Now arguments. A function's arguments sit right after its own return address. So after a run of functions without arguments, you can call one function `fn` with arguments: `&fn`, then `&fn+1` as its return address, then its parameters. But `fn+1` must take no arguments, because the slots after its return address are `fn`'s parameters. That's the 2021 question: with f1 to f5, the easy one to give arguments is the last one.

</Notes>
</Slide>

**[→]** A, 2, 4, 5, 1, 3. The lowest address is the overwritten return address, so `f2` runs first, then each `ret` pops the next word up. D is the trap: it reads top to bottom.

</Notes>

## ROP: chaining gadgets

<Cols columns="1fr 940px" gap={64} align="start">
<div>

- **Gadget**: a few instructions that end in `ret`
- Each `ret` jumps to the next: the stack **is the program**
- `pop; ret` **cleans up arguments**

<Step at={6}>

<p class="small muted">Found in a "letter soup" of existing code. Turing-complete.</p>

</Step>

</div>
<div>

<MemoryStack
  width={940}
  compact

</div>
</Cols>

<Notes>

Now `f1(t); f2(u, v); f3(w, x, y)`. Why is this harder? In a real call, the caller cleans the arguments off the stack after the call returns. In ROP there's no real caller: nothing removes `t`, so when we enter `f2`, the stack still has garbage from `f1`.

The fix: between `f1` and `f2`, put the address of a little piece of code that pops the right number of words, or moves `esp` directly, and then returns. That's a gadget.

Follow `esp`. At the start, `ret` pops `&f1`. **[→]** `f1` runs. To it, the return address is the gadget `pop ebp; ret`, and its argument is `t`. **[→]** When `f1` returns, the gadget pops `t` off the stack, **[→]** and its `ret` jumps to `f2`, with arguments `u` and `v`. **[→]** `f2` returns into a two-pop gadget that removes `u` and `v`, **[→]** and jumps to `f3`.

**[→]** In general, any sequence that ends in `ret`, or more recently `jmp` or `call`, is a gadget. You treat the program and libraries as a letter soup: search for gadgets automatically, then chain them into the behavior you want. Straight-line code is easy, conditionals are possible by changing the stack pointer, so ROP is Turing-complete.

History: before DEP, attackers just injected code. After DEP, around 2007, libc gadgets. After ASLR, gadgets from code at predictable addresses. Today compilers produce position-independent executables, PIE, loaded at random addresses, which makes ROP much harder, so attackers find gadgets at run time.

</Notes>
</Slide>

<Slide title="Defense in depth by layer">


## Defense in depth, by layer

| layer | examples |
| --- | --- |
| **Language** | memory-safe languages, program verification, secure compilation |
| **Compiler / app** | canaries, PIE, instrumentation: <Mark at={1} type="highlight">exploit becomes DoS</Mark> |
| **Operating system** | DEP / W^X, ASLR |
| **Hardware** | NX bit, shadow stack, MTE, TEEs, secure boot |

<Step at={2}>

<p class="big">The common root: <strong>data from outside the perimeter interferes with control flow</strong>.</p>

</Step>

<Notes>

Every attack so far, stack and heap overflows, use-after-free, format strings, integer overflows, shares one root. We'll see it again in web security.

Defense in depth: several layers, because any one can fail. In the language: memory-safe languages like Java, Haskell, Go and Rust, program verification, which is more effort but the only option for critical legacy code, and secure compilation. In the compiler and the application: detect hijacking attempts by monitoring the stack or tagging memory. **[→]** The effect matters: these defenses turn code execution into a DoS, because the program aborts. Still an attack, but much less serious.

In the operating system: prevent malicious code from running, with DEP and ASLR. In the hardware: the instruction set, trusted execution environments, secure boot.

**[→]** And the root cause: data from outside the security perimeter can interfere with the program's control flow, like a buffer stored next to a return address. Even with good principles, one implementation error can break every guarantee.

</Notes>
</Slide>

<Slide title="DEP, ASLR, PIE and bypasses">


## How each is bypassed

| defense | prevents | bypassed by |
| --- | --- | --- |
| **DEP / W^X** | running injected code | <Step at={1} inline>ret2libc, ROP · trouble with JIT</Step> |
| **ASLR** | predicting addresses | <Step at={2} inline>leaking **one** address, spraying, brute force</Step> |
| **KASLR** | locating the kernel | <Step at={3} inline>shuffled only at boot: find the base</Step> |
| **PIE** | code at a fixed address | <Step at={4} inline>leaking the code's base address</Step> |

<Step at={5}>

<p class="big">ASLR's weakness: each region gets a random offset, but its <Mark at={5} type="underline">internal layout is fixed</Mark>.</p>

</Step>

<Notes>

DEP, also called executable space protection or W^X: memory is never writable and executable at the same time. It can be done in hardware with the NX bit, per page, on AMD, Intel and ARM, or emulated in software. Popular OSes have had it since the 2000s. **[→]** Its limits: it doesn't stop code reuse, in fact it's what motivated ROP. And it causes trouble for JIT compilers, which must write code and then run it.

ASLR places the stack, heap, shared libraries and code at random each run, and entropy went from 8 to 24 bits. **[→]** Bypasses: leak an address through another bug, spray, or guess many times inside the same process. A research fix is runtime re-randomization, which reshuffles on forks.

**[→]** Kernel ASLR does the same for the kernel, but only at boot, so the attacker just needs the kernel base. KARL, in OpenBSD, goes further and shuffles the kernel code itself.

**[→]** PIE: the compiler emits code that doesn't depend on absolute addresses, so the program itself can be loaded anywhere. The attacker still just needs the base address of that code.

**[→]** The key weakness: run `cat /proc/self/maps` twice and libc moves, but its parts keep the same distances. Leak one libc address and you know them all.

</Notes>
</Slide>

Stack canaries, named after the canaries miners took into coal mines. The goal: detect stack modification before it's used.

The compiler instruments the entry and exit of each function. On entry it places a value between the local variables and the saved frame pointer and return address. **[→]** A contiguous overflow that wants the return address has to run over the canary first. **[→]** Before using the return address, the function compares the canary with the original. If it changed, the program terminates. So the canary sits just below the saved frame pointer and return address, not below the locals, and it's checked before jumping to the return address, not after.

**[→]** Two variants. Random: at startup the program picks random bytes and uses them for all canaries, so it needs good randomness. **[→]** Terminator: made of `\0`, `\n`, EOF. String functions always stop at those, so a string overflow can't write them back correctly.

**[→]** GCC calls it StackGuard, `-fstack-protector-strong`. In the buffer overflow lab you compiled with it turned off. **[→]** It's simple and practical, but costs one word per call and around 10% performance.

</Notes>

The canary only protects what's above it. So compilers like GCC also change the stack layout. The 2021 test asked you to draw exactly this.

**[→]** Other locals, especially function pointers, go below the buffers. An overflow writes upward, so it can't reach them. If a function pointer were above the buffer, the attacker could change it without ever touching the canary.

**[→]** And the function arguments are copied to the bottom of the stack, below the buffers. The function uses those copies, so overwriting the originals above the return address does nothing.

There's one more extra protection: a shadow stack, which we'll see in a moment.

</Notes>

<Slide title="Defeating canaries">


## Defeating canaries

<Cols columns="1fr 1fr" gap={72}>
<div>

<Reveal start={1}>

- Heap and integer overflows **skip it**
- **Read** the canary with another bug, write it back unchanged
- **Pointer on the stack**: change `ptr` and `value`, and the code does `*ptr = value`

</Reveal>

</div>
<div>

<Step at={4}>

### Byte-by-byte brute force

If the canary survives **forks**, overwrite only byte 1: crash? Try the next value. No crash? Move to byte 2.

<p class="huge" style="margin-bottom:32px"><Mark at={5} type="box" color="green">4 × 256</Mark></p>

<p class="big muted">tries instead of 2³²</p>

</Step>

</div>
</Cols>

<Notes>

How do attackers get past canaries? **[→]** First, heap and integer overflows don't go through the stack frame, so the canary doesn't matter.

**[→]** Second, with another bug that reads memory, like a format string, read the canary and write the same value back during the overflow. The check never notices.

**[→]** Third, existing pointers. If the code has a pointer `ptr` on the stack and writes another local `value` through it, an overflow that changes both, without reaching the canary, gives an arbitrary write. The program does the write for you, for example onto a return address.

**[→]** And brute force. A server that forks for each request gives every child the same canary as the parent. Overwrite just the first canary byte. Crash means wrong, try the next value. No crash means right, move on. **[→]** At most 256 tries per byte, about a thousand for 4 bytes, instead of 2 to the 32. This is also why the lecture warns that restarting after a crash with the same state helps brute force.

</Notes>
</Slide>

## Shadow stack, MTE, CFI

<div class="cards">
<div class="card" data-color="cyan">

### Shadow stack

A second stack with only ret and ebp, compared before returning. **Intel CET**: only `call`/`ret` write it.

</div>
<div class="card" data-color="purple">

### Memory tagging

ARM MTE: pointer and memory share a 4-bit tag. An overflow or a **UAF** raises an exception.

</div>
<div class="card" data-color="orange">

### CFI

Control-flow graph built at compile time, checked at run time. Only **indirect** calls, jumps and returns.

</div>
</div>

<Step at={1}>

<p class="small"><strong>Basic CFI</strong>: any function entry is valid, so calls in the wrong order pass · <strong>classic</strong>: over-approximated CFG (Clang, MS Control Flow Guard) · <strong>CCFI</strong>: a MAC on each address</p>

</Step>

<Notes>

Three newer defenses.

Shadow stack: a redundant stack that holds only control data, the return address and frame pointer. Before returning, the function checks that both stacks agree. With Intel CET, the shadow stack lives in memory that only `call` and `ret` can write. It stops return address overwrites, so it stops ROP chains built from returns.

Memory tagging, ARM MTE: new instructions bind each pointer to its memory region with the same 4-bit tag, compared on every access. An overflow into a neighbor finds a different tag and raises an exception. `free` changes the block's tag, so use-after-free also raises one. It was designed for debugging and extra protection.

Control-flow integrity: the earlier defenses protect memory, CFI protects control flow. At compile time, compute a control-flow graph, the set of valid sources for each target. At run time, check each transfer against it. Direct calls need no check, their target is fixed in the code and the attacker can't change compiled code. Indirect calls, jumps and returns, including function pointers, do.

**[→]** Variants. Basic: any function entry is a valid target, and every function entry must come from a call. It doesn't stop calling functions in a different order, like jumping over an authentication function. Classic: an over-approximated CFG, as in Clang or Microsoft Control Flow Guard. The challenge is computing a precise graph statically. CCFI: store a cryptographic MAC with every address written and check it on use, with the key in a register, never in memory. Many proposals, significant overhead, so hardware support is vital.

</Notes>
</Slide>

<Slide title="Which defense stops what">


## Which defense stops what

| defense | stops | does not stop |
| --- | --- | --- |
| **Canary** | stack overflow up to ret | heap, integer, `%n` writes, leaks |
| **DEP / W^X** | injected shellcode | ret2libc, ROP, JIT spraying |
| **ASLR / PIE** | hard-coded addresses | leaks, spraying, brute force |
| **Shadow stack** | changed return addresses | function pointer hijacks |
| **CFI** | jumps off the CFG | valid edges in a bad order |
| **MTE** | overflows, UAF | bugs within one tag |

<Notes>

This table is the one to memorize for the multiple-choice questions.

A canary only catches a contiguous stack overflow that crosses it on the way to the return address. A format string `%n` writes straight to the return address and never touches it.

DEP only cares whether bytes being executed live in a writable page. Code reuse runs existing code, so it passes.

ASLR and PIE only hide addresses, so anything that reveals or doesn't need an address passes.

A shadow stack protects returns, the backward edges. A hijacked function pointer is a forward edge, that's CFI's job. And basic CFI accepts any legal edge, even in the wrong order.

Memory tagging catches overflows and use-after-free as long as the tags differ. With only 4 bits, two regions can share a tag.

</Notes>
</Slide>

<Notes>

With all these defenses, are attacks still possible? Yes, just more elaborate. The Trident exploit installed the Pegasus spyware on iPhones remotely. It was found in the wild and attributed to the NSO Group.

It chained bugs in the browser and the kernel. A use-after-free in Safari's garbage collector changed the size of an array, giving read and write access to a large memory area. A kernel bug leaked the kernel's location, which defeats KASLR. A bug in Safari's JIT injected shellcode, the JIT exception to W^X again. The earlier bugs helped estimate addresses. And a final kernel bug jailbroke the phone and hid the spyware.

**[→]** The takeaway from the lecture: there must be no holes in the processing of potentially malicious input. One link is all a chain needs.

</Notes>

<Slide title="Program and memory safety">


## Program safety

<Reveal>

- **Program safety**: execution never leaves the language's **defined behavior**
- **Memory safety** ⊂ program safety: no invalid reads, writes or execution
- **Spatial**: depends on location (overflow) · **Temporal**: on lifetime (UAF)
- Strong types check at **compile time**, Python and Java at **run time**: attacks become DoS

</Reveal>

<Step at={5}>

<p class="small">Tools: <strong>dynamic</strong>, automatic, incomplete (valgrind, fuzzing, symbolic execution) · <strong>static</strong>, complete, mostly manual (Frama-C, Dafny)</p>

</Step>

<Notes>

Back to the language layer.

**[→]** Program safety, from programming languages: the program's execution stays within the behavior the language semantics define, for example the C standard. The standard says what happens when you access valid memory and says nothing about the rest. A program that goes there is unsafe. Same for integers: C arithmetic matches real integers only within a range. A program that assumes otherwise is unsafe.

**[→]** Memory safety is a subset: no undefined reads, writes or execution of invalid memory or instructions. **[→]** Spatial safety depends on where you access, that's overflows. Temporal safety depends on the object's lifetime, that's use-after-free.

**[→]** How to get it: strongly typed languages like Java, Haskell and Rust check types and bounds at compile time. Python checks at run time. Interpreted languages raise an exception on a bad access, so a control attack becomes a DoS. Rust mixes static and dynamic checks. The White House and CISA now push memory-safe languages.

**[→]** Even C and assembly can get guarantees with verification tools. Dynamic tools are automatic but incomplete. Static ones are complete but largely manual.

</Notes>
</Slide>

And it showed `if (!aFlag && n < 100) return tab[n];` and asked which CERT rule it breaks: memory safety, because a negative `n` reads before the array.

</Notes>

<Slide title="Beyond safety">


## Beyond safety

<Reveal>

- **Defensive programming**: CERT C Coding Standard
- **Taint analysis**: input is tainted; `printf`, `strcpy` only take untainted data
- **Constant time**: compare all bytes, or timing leaks the password
- **Hardware**: TPM, Intel SGX, ARM TrustZone, UEFI Secure Boot

</Reveal>

<Step at={5}>

<p class="big">Every defense can fail. A crash is still a DoS.</p>

</Step>

<Notes>

**[→]** Defensive programming, like the CERT C Coding Standard, which past tests quote.

**[→]** Taint analysis, a form of information flow analysis: data from `fgets` on the network is marked tainted, and critical functions like `printf`'s format or `strcpy` only accept untainted arguments. Passing user input as a format string becomes a type error.

**[→]** Constant-time analysis against timing side channels. The lecture's password check stops at the first wrong character, so the response time tells you how many characters you got right. Also secure compilation: proving the compiler adds no security bugs.

**[→]** Hardware: a TPM is a secure crypto-processor, SGX and TrustZone are trusted execution environments, and UEFI Secure Boot only runs firmware trusted by the manufacturer.

**[→]** Why do vulnerabilities still exist? Programmers make mistakes and often don't see the consequences, and general-purpose languages weren't designed for security. One study even found that people using AI assistants wrote less secure code while feeling more confident. Defense in depth means many layers, but all can fail, and there's no final fallback. Even when they work, we're still exposed to DoS. And recovering from a crash by restoring the same state makes brute force easier, as with forked canaries.

</Notes>
</Slide>
