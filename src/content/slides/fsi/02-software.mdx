<Notes>

Antes de partir memória, temos de saber como ela está organizada. Isto é Linux em x86, e a memória é virtual, gerida pelo sistema operativo.

Dos endereços altos para os baixos: argumentos e variáveis de ambiente lá em cima, depois a stack, depois o heap, depois as globais e por fim o código.

**[→]** A stack cresce para baixo, para endereços mais pequenos. Guarda variáveis locais, argumentos de funções e endereços de retorno. O `x` vive aqui. Guarda esta ideia, porque é por isso que um overflow na stack chega ao endereço de retorno.

**[→]** O heap cresce para cima e é memória pedida em tempo de execução, com `malloc`. O bloco para onde o `p` aponta está no heap; o próprio `p` está na stack.

**[→]** As globais: o `g` tem valor inicial, vai para data; o `z` não tem, vai para o bss, que o exec põe a zeros.

**[→]** E o text é o código do programa, nos endereços baixos.

<Notes>

Agora o que acontece numa chamada de função. O `main` chama `f(1, 2)`, e `f` tem um buffer de 16 bytes.

Há dois registos importantes: o `esp`, stack pointer, que aponta para o fim da stack, e o `ebp`, frame pointer, que marca o início do frame atual.

**[→]** Primeiro, o caller empurra os argumentos, do último para o primeiro. Por isso o `b` fica acima do `a`.

**[→]** Depois a instrução `call` empurra o endereço de retorno: para onde o programa volta quando `f` acabar.

**[→]** Já dentro de `f`, guarda-se o `ebp` antigo, o do main, e o `ebp` passa a apontar para aqui.

**[→]** Por fim reserva-se espaço para as variáveis locais, o `buf`, e o `esp` desce.

**[→]** Repara na ordem, de cima para baixo: argumentos, endereço de retorno, ebp guardado, buffer. O buffer está **abaixo** do endereço de retorno, e as cópias escrevem para **cima**. Já estás a ver onde isto vai dar.

</Notes>

## Stack smashing

<Cols columns="1fr 1000px" gap={64} align="start">
<div>

```c
void f(char *str) {
  char buf[128];
  strcpy(buf, str);
}
```

<Reveal start={1}>

- `strcpy` copia **até ao `\0`**, sem olhar para o tamanho de `buf`
- Se `str` vem de **fora do perímetro**, o atacante escolhe os bytes
- Causa raiz: **não há separação entre código e dados**

</Reveal>

</div>

<Notes>

Este é o ataque clássico. `f` tem um buffer de 128 bytes e faz `strcpy` de uma string que vem de fora.

**[→]** O `strcpy` copia até encontrar o byte zero. Não sabe nem quer saber o tamanho do destino. Se a string tiver mais de 128 bytes, a cópia enche o buffer e continua.

**[→]** Se essa string vem de fora do perímetro de segurança, quem a escolhe é o atacante. **[→]** E o problema de fundo é que na stack não há separação entre código e dados: o endereço de retorno, que controla o fluxo do programa, está ao lado de dados controlados pelo atacante.

Continua a cópia: **[→]** passa por cima do ebp guardado, **[→]** e por cima do endereço de retorno. Quando a função faz `ret`, salta para 0x41414141, que é "AAAA". Crash.

Mas o atacante não quer um crash, quer controlo. **[→]** Se em vez de A's meter código no buffer e escrever no endereço de retorno o endereço do buffer, o `ret` salta para o código dele. Isto é stack smashing.

</Notes>

<Notes>

Vamos ver isto a acontecer. Isto é uma simulação, mas segue as regras a sério: buffer de 16 bytes, little-endian, e o `strcpy` escreve sempre um `\0` no fim. Cada linha é uma palavra de 4 bytes, endereços a crescer para cima.

Com "rodrigo" está tudo bem: 7 bytes mais o zero cabem.

**[→]** 15 A's: 15 bytes mais o `\0` são exatamente 16. Ainda cabe.

**[→]** 16 A's: agora o `\0` já não cabe e vai parar ao primeiro byte do ebp guardado. Um único byte a mais! Isto parece inofensivo, mas é o "poisoned NUL byte": o ebp do caller fica a apontar para outro sítio, e quando o caller retornar, vai buscar o endereço de retorno a um sítio que o atacante controla.

**[→]** Agora 16 A's, BBBB e CCCC. O BBBB vai para o ebp e o CCCC para o endereço de retorno: 0x43434343. Quando a função retornar, salta para lá e crasha.

**[→]** E agora a sério: começo com NOPs, 0x90, depois uns bytes de shellcode, BBBB para o ebp, e no fim o endereço do próprio buffer, escrito ao contrário por ser little-endian. O retorno aponta para o buffer: o CPU executa o nosso input.

Se estiveres a ver isto no site, escreve tu na caixa. Podes usar `\x41` para meter bytes.

</Notes>

## Shellcode e NOP sled

<Cols columns="1fr 960px" gap={64} align="start">
<div>

<Reveal class="small">

- **Shellcode**: código máquina que abre uma shell, `execve("/bin/sh", …)`. O clássico tem 33 bytes.
- O endereço exato do buffer **varia**: à frente vai um **NOP sled** (0x90). Cair em qualquer NOP serve.
- **Sem `\0`** no payload: o `strcpy` parava no primeiro byte nulo.
- Mais robusto: pôr o shellcode **acima** do ret e apontar o ret para um `jmp esp`.

</Reveal>

</div>
<div>

<Notes>

O código que o atacante injeta chama-se shellcode, porque normalmente abre uma shell: chama `execve` com "/bin/sh". Compilado, o clássico tem 33 bytes.

**[→]** O problema: o atacante não sabe o endereço exato do buffer, porque varia com o ambiente, as variáveis de ambiente, etc. **[→]** Solução: antes do shellcode mete uma rampa de NOPs, o NOP sled. Se o retorno cair em qualquer sítio da rampa, **[→]** o CPU vai executando NOPs, que não fazem nada além de avançar, **[→]** até chegar ao shellcode.

Pormenor que sai: o payload não pode ter bytes zero, porque o `strcpy` parava aí e o resto não era copiado.

E um truque para ser mais robusto: meter o shellcode acima do endereço de retorno e apontar o retorno para uma instrução `jmp esp` que já exista no programa. Assim não precisas de adivinhar endereço nenhum.

</Notes>
</Slide>

## 1988: o Morris worm

<Cols columns="1fr 1fr" gap={72}>
<div>

```c
// fingerd
char line[512];
// ...
gets(line);
```

<Step at={1}>

O `gets` lê **tudo** o que o cliente enviar. 536 caracteres chegam ao endereço de retorno.

</Step>

<Step at={2}>

<p class="small muted">1972 conceito documentado · 1988 Morris worm · 1996 "Smashing the Stack for Fun and Profit" (Aleph One) · jailbreaks de consolas</p>

</Step>

</div>
<div>

<Step at={3}>

| função | problema |
| --- | --- |
| `strcpy`, `strcat` | não conhecem o tamanho do destino |
| `gets`, `scanf("%s")` | leem até onde o input quiser |
| `strncpy` | limita, mas **pode não terminar com `\0`** |

</Step>

<Step at={4}>

<p class="small">E código caseiro que <strong>assume input confiável</strong>: libpng 2004, off-by-one no realpath 2003, poisoned NUL byte 1998 e 2014.</p>

</Step>

</div>
</Cols>

<Notes>

O primeiro uso hostil de um buffer overflow foi o Morris worm, em 1988. O bug estava no `fingerd`, e é o "spot the vulnerability" da aula.

**[→]** O buffer tem 512 bytes, mas o `gets` lê tudo o que o cliente mandar. O código assume que o input cabe. 536 caracteres chegam para reescrever o endereço de retorno.

**[→]** Um pouco de história: o conceito estava documentado desde 1972, o Morris worm é de 1988, e em 1996 o Aleph One publicou o "Smashing the Stack for Fun and Profit", que tornou isto mainstream.

**[→]** Porque é que continua a ser tão comum? Funções da libc que não sabem o tamanho do destino: `strcpy`, `strcat`, `gets`, `scanf`. E atenção ao `strncpy`: limita o tamanho, mas se a string for comprida demais não mete o `\0` no fim. Esta é uma rasteira clássica.

**[→]** E código feito à mão que assume que o input é confiável. A libpng em 2004 saltava a verificação de tamanho num caminho de erro, o realpath tinha um off-by-one, e o poisoned NUL byte que vimos na demo foi explorado em 1998 e outra vez em 2014.

</Notes>
</Slide>

## "Porque não usamos só linguagens seguras?"

<Reveal>

- As linguagens seguras **compilam para** ou **usam** bibliotecas em C / LLVM
- VMs, browsers e sistemas operativos continuam escritos em **linguagens de baixo nível**
- Código criptográfico é **otimizado à mão**
- Os ataques **encadeiam** várias vulnerabilidades
- O input é **sempre** potencialmente malicioso

</Reveal>

<Step at={6}>

<p class="big">Overflow = aceder fora da memória alocada. Está no <strong>CWE Top 25</strong>: #1 out-of-bounds write, #4 use-after-free, #7 out-of-bounds read.</p>

</Step>

<Notes>

Pergunta razoável: se C é assim tão perigoso, porque não usamos só linguagens seguras?

**[→]** Porque essas linguagens compilam para C ou usam bibliotecas em C e LLVM por baixo. **[→]** Porque as VMs, os browsers e os sistemas operativos continuam escritos em linguagens de baixo nível. **[→]** Porque o código de criptografia é otimizado à mão. **[→]** Porque os ataques encadeiam várias vulnerabilidades: basta uma peça insegura. **[→]** E porque o input é sempre potencialmente malicioso, seja qual for a linguagem.

**[→]** E não é um problema antigo: no CWE Top 25 de 2023, out-of-bounds write é o número 1, use-after-free o 4 e out-of-bounds read o 7.

</Notes>

## Heap overflow

<Cols columns="1fr 960px" gap={64} align="start">
<div>

```c
char *a = malloc(5);
char *b = malloc(5);
strcpy(a, input);  // > 5 bytes
free(b);
```

<Reveal start={3} class="small">

- Alvos: **ponteiros para funções** (vtables, GOT)
- Layout imprevisível: **mais difícil** que na stack
- **Heap spraying**: encher a memória de NOP sled + shellcode

</Reveal>

</div>
<div>

<Notes>

No heap a ideia é a mesma: dois blocos de 5 bytes, e um `strcpy` de algo maior para o primeiro.

Mas no heap não há endereço de retorno. O que há? Cada bloco do malloc tem metadados: o tamanho e, quando está livre, dois ponteiros, `fd` e `bk`, para a lista de blocos livres.

**[→]** O overflow de `a` escreve por cima dos metadados do bloco seguinte. **[→]** Quando o programa faz `free`, o alocador mexe nessa lista ligada e escreve através de `fd` e `bk`. Como o atacante controla os dois, controla uma escrita: por exemplo, trocar o endereço de `exit()` na GOT pelo endereço do shellcode. Isto é o "smashing the heap".

**[→]** Outros alvos: o heap está cheio de ponteiros para funções, como as vtables dos objetos C++ ou a GOT das bibliotecas dinâmicas, e também handlers de exceções e buffers de longjmp.

**[→]** É mais difícil do que na stack, porque o C só garante que cada bloco é contíguo, e o layout depende do alocador, do SO e do hardware.

**[→]** Nos browsers o layout é imprevisível, por isso usa-se heap spraying: JavaScript malicioso enche a memória com cópias de NOP sled mais shellcode, para que um ponteiro corrompido caia muito provavelmente numa delas.

</Notes>
</Slide>

## Use-after-free

<Cols columns="1fr 820px" gap={64} align="start">
<div>

<CodeSteps steps={["1", "2", "3-4", "5"]}>

```c
char *ptr = malloc(100);
free(ptr);
char *ptr2 = malloc(100);
strcpy(ptr2, "admin / S3cret!");
puts(ptr);   // ptr ficou pendurado
```

</CodeSteps>

<Step at={5}>

<p class="small">No Chrome, <strong>70%</strong> dos bugs de segurança são de memória. Só UAF: <strong>~36%</strong>.</p>

</Step>

</div>

<Notes>

Use-after-free: usar memória que já foi libertada.

**[→]** Pedimos 100 bytes, o `ptr` aponta para lá. **[→]** Fazemos `free`. O bloco volta para o alocador, mas o `ptr` não muda: continua a apontar para o mesmo endereço. É um dangling pointer.

**[→]** O próximo `malloc(100)` devolve exatamente o mesmo bloco, e alguém mete lá credenciais. **[→]** Agora o `puts(ptr)` lê, através do ponteiro antigo, os dados de outra pessoa.

Porque é que isto dá controlo, e não só uma fuga? Se o objeto libertado era um objeto C++ com vtable, e o atacante conseguir pôr dados seus nesse bloco reutilizado, a próxima chamada virtual através do ponteiro antigo salta para onde ele quiser. Pode nem crashar, o que o torna imprevisível.

**[→]** É muito comum em browsers: no Chrome, 70% dos bugs de segurança são de memória, e só use-after-free são uns 36%.

</Notes>

## Integer overflow: OpenSSH 3.3 (2002)

<Cols columns="1.3fr 1fr" gap={64} align="start">
<div>

<CodeSteps steps={["1", "3", "4-5"]}>

```c
nresp = packet_get_int();
if (nresp > 0) {
  response = xmalloc(nresp*sizeof(char*));
  for (i = 0; i < nresp; i++)
    response[i] = packet_get_string(NULL);
}
```

</CodeSteps>

</div>
<div>

<Step at={1}>

O atacante envia `nresp = 0x40000000` (2³⁰)

</Step>

<Step at={2}>

<p class="big">2³⁰ × 4 = 2³² → em 32 bits <Mark at={2} type="circle">= 0</Mark></p>

`xmalloc(0)`: buffer minúsculo

</Step>

<Step at={3}>

O ciclo escreve 2³⁰ ponteiros nele: **heap overflow**

</Step>

<Step at={4}>

<p class="small muted">Outras formas: truncar num cast (int → short), larguras misturadas (<code>unsigned short len</code> vs <code>size_t</code>), sinal: <code>0xffffffff</code> é −1 com sinal.</p>

</Step>

</div>
</Cols>

<Notes>

Integer overflow, e este código saiu em dois testes. O `nresp` vem do pacote de rede, portanto é controlado pelo atacante.

**[→]** O atacante manda `nresp` igual a 2 elevado a 30.

**[→]** O código multiplica pelo tamanho de um ponteiro, 4 bytes. 2 elevado a 30 vezes 4 é 2 elevado a 32, que em 32 bits dá a volta e fica zero. Aritmética modular. O `xmalloc` aloca zero bytes, ou quase.

**[→]** E depois o ciclo, que confia no `nresp` original, escreve mais de mil milhões de ponteiros nesse buffer minúsculo. Heap buffer overflow.

A cadeia é: inteiro controlado pelo atacante, overflow num cálculo, buffer pequeno demais, buffer overflow, e daí execução de código ou crash. E um crash, um DoS, já é um ataque válido.

**[→]** Outras formas de integer overflow: truncar num cast, comparar larguras diferentes, ou o sinal: 0xffffffff é −1 com sinal e 4 mil milhões sem sinal. Um `if (size < sizeof(x))` com um size negativo passa a verificação.

</Notes>
</Slide>

Nem é preciso escrever: ler fora dos limites também é grave.

Há dois sabores. Limite inferior: verificas `i < len` mas esqueces `i >= 0`, e um índice negativo lê antes do array. Limite superior: o off-by-one, `<=` em vez de `<`.

<Slide title="DEP, ASLR e reutilização de código">


## Já não dá para injetar código

<div class="cards">
<div class="card" data-color="blue">

### DEP / W^X

Uma página é **escrevível ou executável**, nunca as duas. O shellcode na stack já não corre.

</div>
<div class="card" data-color="green">

### ASLR

Os endereços são **baralhados** em cada execução. Já não sabes onde está o buffer.

</div>
<div class="card" data-color="orange">

### JIT spraying

Constantes do atacante compiladas pelo JIT são instruções válidas a meio. O código do JIT é executável (contorna DEP) e espalhado (contorna ASLR).

</div>
</div>

<Step at={1}>

<p class="big"><strong>Reutilização de código</strong>: usa o que já é executável. A libc tem <code>system()</code> (corre um comando) e <code>mprotect()</code> (muda permissões de memória).</p>

</Step>

<Notes>

As defesas modernas tornam a injeção de código difícil. Duas principais.

DEP, ou W^X: uma página de memória ou é escrevível ou é executável, nunca as duas. A stack é escrevível, logo não é executável: o shellcode lá metido já não corre.

ASLR: os endereços da stack, do heap e das bibliotecas mudam em cada execução. Já não sabes para onde apontar.

Uma forma de dar a volta aos dois é JIT spraying. Os JITs de JavaScript ou Flash compilam constantes do atacante para código. Se saltares para o meio de uma instrução, os bytes da constante são lidos como NOPs e outras instruções. Esse código é executável, por isso passa o DEP, e está espalhado pela memória, por isso passa o ASLR.

**[→]** A ideia geral, porém, é: se não podes injetar código, usa o código que já lá está. As bibliotecas estão em memória executável, e a libc tem tudo o que precisas: `system` para correr comandos e `mprotect` para mudar permissões de memória.

</Notes>
</Slide>

## ROP: encadear gadgets

<Cols columns="1fr 940px" gap={64} align="start">

- **Gadget**: instruções que acabam em `ret`

<Step at={6}>

<Notes>

Return-oriented programming. Generalizamos o return-to-libc: em vez de uma função, encadeamos muitas.

Um gadget é uma sequência curta de instruções que acaba em `ret`. O truque: cada `ret` tira o próximo endereço da stack e salta para lá. Então se a stack tiver uma lista de endereços, cada gadget, ao terminar, salta para o seguinte. A stack passa a ser o programa, e o esp faz de program counter.

Vamos seguir o esp. Ao início o `ret` tira `&fun1`. **[→]** A `fun1` corre; para ela, o endereço de retorno é o gadget `pop ebp; ret` e o argumento é `t`. **[→]** Quando `fun1` retorna, entra o gadget: o `pop` tira o `t` da stack, para o limpar. **[→]** E o `ret` salta para `fun2`, com argumentos `u` e `v`. **[→]** A `fun2` retorna para um gadget com dois pops, que limpa `u` e `v`, **[→]** e salta para `fun3`.

**[→]** É por isso que se diz que é como uma carta de resgate: recortas instruções que já existem no binário e colas uma atrás da outra. É Turing-completo, até dá para fazer condições mexendo no stack pointer.

Hoje o PIE, executáveis independentes da posição, torna o ROP bem mais difícil, por isso os atacantes procuram gadgets em tempo de execução.

</Notes>

## Defesa em profundidade, por nível

| nível | exemplos |
| --- | --- |
| **Linguagem** | linguagens memory-safe (Java, Haskell, Go, Rust), verificação, compilação segura |
| **Compilador / aplicação** | canários, PIE, instrumentação: <Mark at={1} type="highlight">o exploit vira DoS</Mark> |
| **Sistema operativo** | DEP / W^X, ASLR |
| **Hardware** | bit NX, shadow stack (Intel CET), MTE, TEEs, secure boot |

<Step at={2}>

<p class="big">A raiz comum: <strong>dados de fora do perímetro interferem com o fluxo de controlo</strong> (um buffer ao lado de um endereço de retorno).</p>

</Step>

<Notes>

Agora as defesas. A ideia é defesa em profundidade: várias camadas, porque qualquer uma pode falhar. Os slides organizam-nas por nível.

Na linguagem: usar linguagens memory-safe, verificação de programas, compilação segura. No compilador e na aplicação: detetar o desvio de controlo, com canários ou instrumentação. **[→]** E repara no efeito: estas defesas transformam execução de código em DoS, porque o programa aborta. Continua a ser um ataque, mas muito menos grave.

No sistema operativo: impedir a execução de código malicioso, com DEP e ASLR. No hardware: o bit NX, shadow stacks, memory tagging, ambientes de execução confiáveis, secure boot.

**[→]** E a raiz de tudo isto é sempre a mesma: dados que vêm de fora do perímetro conseguem interferir com o fluxo de controlo.

</Notes>
</Slide>

<Slide title="DEP e ASLR, e como se contornam">


## DEP e ASLR, e como se contornam

| defesa | impede | contorna-se com |
| --- | --- | --- |
| **DEP / W^X** (bit NX) | executar código injetado | <Step at={1} inline>ROP, return-to-libc · problemas com JIT</Step> |
| **ASLR** | prever endereços | <Step at={2} inline>fuga de **um** endereço, spraying, força bruta no mesmo processo</Step> |
| **KASLR** | saber onde está o kernel | <Step at={3} inline>só baralha no arranque: basta a base do kernel</Step> |

<Step at={4}>

<p class="big">O ponto fraco do ASLR: cada região tem um offset aleatório, mas o <Mark at={4} type="underline">layout dentro dela é fixo</Mark>. Um leak revela o resto.</p>

</Step>

<Notes>

DEP, ou W^X, ou executable space protection: a memória nunca é escrevível e executável ao mesmo tempo. Há suporte de hardware, o bit NX, por página. **[→]** Não trava reutilização de código: aliás, foi a motivação do ROP. E dá problemas aos JITs, que precisam de escrever código e executá-lo.

O ASLR baralha a stack, o heap, as bibliotecas e o código em cada execução. A entropia passou de 8 para 24 bits. **[→]** Contorna-se com uma fuga de endereço através de outra vulnerabilidade, com spraying, ou à força bruta dentro do mesmo processo.

**[→]** O KASLR faz o mesmo ao kernel, mas só baralha no arranque, por isso basta descobrir a base do kernel.

**[→]** E o ponto que mais interessa: o ASLR dá um offset aleatório a cada região, mas dentro da região o layout é fixo. Se correres `cat /proc/self/maps` duas vezes, a libc muda de sítio mas os segmentos dela mantêm as mesmas distâncias. Basta saberes um endereço da libc e sabes todos.

</Notes>
</Slide>

<Notes>

Os canários de stack, o nome vem dos canários nas minas de carvão.

O compilador mete um valor secreto entre as variáveis locais e o ebp guardado mais o endereço de retorno. **[→]** Para um overflow chegar ao endereço de retorno, tem de passar por cima do canário. **[→]** Antes de retornar, a função compara o canário com o valor original. Se mudou, aborta. Atenção à pergunta de teste: o que impede o smash é verificar se o **valor** mudou quando a função vai saltar para o endereço de retorno. A posição não é segredo.

**[→]** Há dois tipos. Aleatório, que precisa de boa aleatoriedade. **[→]** E terminador, feito de `\0`, `\n` e EOF: as funções de strings param nesses caracteres, por isso não o conseguem reescrever com o valor certo.

**[→]** No GCC é o `-fstack-protector-strong`. **[→]** É simples, mas custa espaço, uma palavra por chamada, e uns 10% de desempenho.

<Slide title="Contornar canários">


## Contornar canários

<Cols columns="1fr 1fr" gap={72}>
<div>

<Reveal start={1}>

- Heap overflow e integer overflow **nem passam pela stack**
- **Ler** o canário com outro bug e escrevê-lo de volta igual
- **Ponteiro na stack**: o overflow muda `ptr` e `value` sem tocar no canário, e o próprio código faz `*ptr = value`

</Reveal>

</div>
<div>

<Step at={4}>

### Força bruta byte a byte

Se o canário se mantém entre **forks**, escreve só o 1.º byte: crasha? Tenta o seguinte. Não crashou? Acertaste. Passa ao 2.º.

<p class="huge"><Mark at={5} type="box" color="green">4 × 256</Mark></p>

<p class="big muted">tentativas, em vez de 2³²</p>

</Step>

</div>
</Cols>

<Notes>

Como se contornam os canários? **[→]** Primeiro, heap overflows e integer overflows nem passam pela stack, por isso o canário é irrelevante.

**[→]** Segundo, se tiveres outro bug que deixe ler memória, lês o canário e escreves o mesmo valor por cima. Ele nunca nota.

**[→]** Terceiro, o truque do ponteiro: se houver um ponteiro e um valor na stack entre o buffer e o canário, o overflow muda os dois sem chegar ao canário, e depois o próprio código faz `*ptr = value`. Escreves onde quiseres, por exemplo num endereço de retorno.

**[→]** E força bruta byte a byte. Num servidor que faz fork para cada pedido, o canário do filho é igual ao do pai. Escreves só o primeiro byte do canário. Se crashar, estava errado, tentas o seguinte. Se não crashar, acertaste, e passas ao segundo byte. **[→]** São no máximo 256 tentativas por byte: para 4 bytes, mil e tal tentativas, em vez de 2 elevado a 32.

</Notes>
</Slide>

<Slide title="Shadow stack, MTE e CFI">


## Mais defesas: shadow stack, MTE, CFI

<div class="cards">
<div class="card" data-color="cyan">

### Shadow stack

Uma segunda stack só com dados de controlo (ret, ebp). Compara antes de retornar. **Intel CET**: só `call`/`ret` lhe escrevem.

</div>
<div class="card" data-color="purple">

### Memory tagging (ARM MTE)

Ponteiro e memória partilham uma tag de 4 bits. Overflow → exceção. `free` muda a tag → **UAF** também dá exceção.

</div>
<div class="card" data-color="orange">

### CFI

Grafo de controlo calculado na compilação, verificado em execução. Só **chamadas indiretas, saltos e retornos**.

</div>
</div>

<Step at={1}>

<p class="small"><strong>CFI básico</strong>: qualquer início de função serve (não trava chamadas pela ordem errada, como saltar a autenticação) · <strong>clássico</strong>: CFG sobre-aproximado (Clang, MS CFG) · <strong>CCFI</strong>: MAC em cada endereço, chave num registo. Custo alto: precisa de hardware.</p>

</Step>

<Notes>

Três defesas mais recentes.

Shadow stack: uma segunda stack redundante que só guarda dados de controlo, o endereço de retorno e o frame pointer. Antes de retornar compara as duas. Com Intel CET, a shadow stack só pode ser escrita pelas instruções `call` e `ret`.

Memory tagging, no ARM: cada ponteiro e cada região de memória têm uma tag de 4 bits, e cada acesso verifica se batem certo. Um overflow para o bloco vizinho apanha uma tag diferente e dá exceção. E o `free` muda a tag do bloco, por isso um use-after-free também dá exceção.

Control-flow integrity: na compilação calcula-se o grafo de controlo, e em execução verifica-se que cada salto o respeita. Chamadas diretas não precisam de proteção; as indiretas, os saltos e os retornos sim.

**[→]** Há variantes. A básica aceita qualquer início de função como destino, por isso não trava chamar funções pela ordem errada, como saltar a autenticação. A clássica usa um grafo sobre-aproximado, como o Clang ou o Control Flow Guard da Microsoft; o difícil é calcular um grafo preciso estaticamente. E a CCFI guarda um MAC com cada endereço, com a chave num registo, nunca em memória. Tudo isto custa desempenho, por isso o suporte de hardware é essencial.

</Notes>
</Slide>

## Mesmo assim: Trident → Pegasus (iOS)

<Notes>

Com isto tudo, ainda há ataques? Há. O Trident, que instalava o Pegasus no iOS, encadeou quatro falhas: um use-after-free no garbage collector do Safari, para ganhar memória de leitura e escrita; uma fuga de informação para saber onde estava o kernel, que é o contorno do KASLR; um bug no JIT do Safari para injetar shellcode; e um bug no kernel para o jailbreak e para não ser detetado. Atribuído à NSO. A lição: não pode haver buracos no processamento de input malicioso.

**[→]** Memory safety é um subconjunto de program safety. Segurança espacial depende do sítio onde acedes, que é o overflow. Segurança temporal depende do tempo de vida do objeto, que é o use-after-free. Linguagens fortemente tipadas verificam na compilação, o Python verifica em execução, e o Rust mistura os dois.

**[→]** Para lá disso: taint analysis, em que o input do utilizador fica marcado como sujo e as funções críticas só aceitam dados limpos; código em tempo constante, porque uma comparação de passwords que sai ao primeiro caractere errado revela quantos acertaste; e hardware: TPM, enclaves como o SGX e a TrustZone, e secure boot.

E porque é que as vulnerabilidades continuam a existir? Os programadores erram, as linguagens não foram desenhadas para segurança, e um estudo mostrou que quem usa assistentes de IA escreve código menos seguro e fica mais confiante de que é seguro.

</Notes>
