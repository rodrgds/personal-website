<Slide title="HTTP and cookies">


## HTTP and cookies

```text
https://sigarra.up.pt:443/fcup/en/cur_view?pv_ano=2022#objectives
scheme  domain       port path             query      fragment
```

<Reveal>

- **Stateless**. Methods: GET reads, POST creates, PUT replaces, PATCH changes part, DELETE
- In practice **GET has side effects**, and its parameters land in **server logs and browser history**
- **Cookies** add state: the server sets one, the browser stores it and sends it on **every** request to that server
- The cookie jar is **shared**: tab 2 sends the cookie that tab 1 got at login

</Reveal>

<Notes>

Web security sits on top of things that look harmless, so I start with HTTP. A URL has a scheme, a domain with an optional port, a path, the query and the fragment. Keep this picture: an origin will be the first three parts.

**[→]** HTTP is stateless: every request stands alone. The server answers with a status code and an optional body.

**[→]** GET was never supposed to change server state, but it often does: a bank transfer as a GET with the amount in the URL, and those parameters end up in the server log and the browser history. Meanwhile POST got used for almost everything with side effects.

**[→]** Servers need to know that two requests belong together, so we got cookies. The server sends a cookie, for example after a successful login, the browser stores it, and sends it back every time a URL on that server is accessed. Uses: sessions, customization, tracking.

**[→]** And the jar is shared across tabs. Log in to the bank in one tab, and requests to the bank from any other tab carry the same cookie. That is the root of CSRF, which comes later. HTTP/2 and HTTP/3 changed transport and performance, but the attacks we study are mostly independent of that.

</Notes>
</Slide>

<Slide title="Pages are programs">


## A page is a program

<Reveal>

- The browser renders HTML and CSS, runs **JavaScript**, fetches sub-resources: a **domain-specific virtualization** system
- **Frames and iframes** give a screen area to another origin, isolated: the parent survives a broken or malicious child
- The **DOM** is the object tree of the page. Loading is recursive and driven by events

</Reveal>

<Step at={4}>

<p class="big">JavaScript reads and changes <Mark at={4} type="underline" color="red">everything</Mark>.</p>

</Step>

<Notes>

A web page is not a document, it is a program.

**[→]** Each browser window renders HTML and CSS, runs JavaScript or WebAssembly, requests sub-resources like images and scripts, and reacts to user events.

**[→]** A window can mix content from different origins with frames and iframes. Why use them? To hand a screen area to another origin, and to get the browser's frame isolation for free: if the child fails, or is malicious, the parent keeps working.

**[→]** The DOM is the tree of objects that represents the page. Loading is recursive, and may never finish.

**[→]** JavaScript can read and change all of it: manipulate the DOM, make requests, read browser data, even learn about the hardware. Exceptionally powerful and dangerous.

</Notes>
</Slide>

## Who is the attacker?

<Step at={1}>

<div class="cards" style="--n:3">
<div class="card" data-color="blue">

### In the browser

Exploits or malware. We assume the browser is **trusted**.

</div>
<div class="card" data-color="orange">

### Network

Controls the channel. We assume **secure channels**.

</div>
<div class="card" data-color="red">

### Web attacker

Controls part of the web app, client or server. **Our focus.**

</div>
</div>

</Step>

<Step at={2}>

<p class="lede">The attacker can be the <strong>server</strong>, the <strong>user</strong>, a <strong>page</strong>, or part of a page. We rely on <strong>browser isolation</strong>.</p>

</Step>

<Notes>

Who do we defend against? Server and user can be malicious, and the browser can have bugs or malicious extensions.

**[→]** Three attacker models. The attacker in the browser: we assume the browser itself is trusted, because that was software and systems security. The network attacker, who controls the channel: we assume secure channels, that is network security later. And the web attacker, who controls part of the web application: that is this whole part.

**[→]** The web attacker has variants. If he controls the server, we protect the client machine. If he is a user, he can change the page content, so we trust only browser and server protections. If he is a web page, page A must not interfere with or observe page B. If he controls part of a page, like an ad in a sub-frame, it must not interfere with the host page. And the host page must not interfere with the object it embeds, for example for phishing. In every page case, what we trust is browser isolation.

</Notes>
</Slide>

<Slide title="Embed, but do not inspect">


## Embed, but do not inspect

| Page A **can** | Page A **cannot** |
| --- | --- |
| run a script from B (in A's context) | read or change that script's code |
| show a page from B in an iframe | read or change the iframe's DOM |
| show an image from B | read its pixels (but sees its **size**) |
| load CSS and fonts from B | read their text |

<Step at={1}>

<p class="lede">Frames can talk with <code>postMessage</code>: the receiver must check <code>event.origin</code>.</p>

</Step>

<Notes>

What does the SOP allow when a page pulls in content from another origin? The rule of thumb: you can include, you cannot inspect.

A script from a CDN runs inside your origin, with your powers, but your code cannot read its source. That is how your newspaper runs Google Analytics with full access to its DOM. You can frame another origin, but you cannot touch its DOM. When you can, that is Cross-Frame Scripting, XFS, for example stealing keystrokes from a framed bank page. You can show an image, but not read its pixels. Yet you can see its size, and that leaks: a profile photo that has a different size when the user is logged in tells you the user's state. So public resources are not automatically harmless.

**[→]** Frames from different origins can still exchange messages. The receiver must check event.origin and drop anything from an origin it does not expect.

</Notes>
</Slide>

<Slide title="Requests across origins">


## Requests across origins

| From origin A to B | Send? | Read the response? |
| --- | --- | --- |
| HTML link, image or form | <Step at={1} inline>yes</Step> | <Step at={1} inline>no</Step> |
| JavaScript GET | <Step at={2} inline>yes</Step> | <Step at={2} inline>only with CORS</Step> |
| JavaScript POST | <Step at={3} inline>same origin only</Step> | <Step at={3} inline>no</Step> |

<Step at={4}>

<p class="lede">The SOP protects the <strong>response</strong>, not the <strong>request</strong>.</p>

</Step>

<Notes>

This table answers several test questions.

**[→]** HTML on page A can make requests to any origin: a link, an image, a form that posts. The side effects are allowed, so you can send data to an external service. The browser may process the response, for example to draw the image or the frame, but A's code cannot analyze it.

**[→]** JavaScript with XMLHttpRequest, fetch or jQuery's ajax can send a GET to any origin, but it only sees the response if it is the same origin, or if the other server opts in with CORS.

**[→]** And by default, a JavaScript POST can only go to the same origin. That is the lecture's rule, and the tests use it: a page in A can post to B with a form, but script in A cannot post to B.

**[→]** The one sentence to keep: the SOP protects the response, not the request. The request leaves, with its cookies, and that is exactly what CSRF abuses.

</Notes>
</Slide>

### Simple

### Preflighted

<Diagram
  fontSize={24}

  source={`sequenceDiagram
  participant A as Page A

/>

</Step>

</div>

<Notes>

Cross-Origin Resource Sharing lets server B relax the SOP, mostly for requests that JavaScript makes. Two kinds.

On the left, a simple request, meant for requests without side effects on B. The browser sends it first, then checks whether the response lets code from A read it. B lists the allowed origins in the Access-Control-Allow-Origin header. Even here there is a risk: response time or status code can leak, an XS-Leak.

**[→]** On the right, a preflighted request, for requests that may have side effects. The browser first sends a dummy request with no side effects and checks whether B allows A. Only if it does, the browser sends the real request. The exam difference: simple means request first, check after; preflighted means check first, request after.

</Notes>

<Slide title="When is a cookie sent?">


## When is a cookie sent?

<p class="lede">A cookie's origin is <strong>(domain, path)</strong>. Scheme and port are optional.</p>

<Reveal>

- **Domain**: the cookie's domain is a **suffix** of the URL's host
- **Path**: the cookie's path is a **prefix** of the URL's path
- A site sets cookies for its domain and **parent domains**, never a **public suffix** like `.com` or `.co.uk`

</Reveal>

<Step at={4}>

<p class="lede"><code>Domain=fsi.pt</code> goes to <code>login.fsi.pt</code>, and <code>Path=/my</code> goes to <code>/my/home</code>.</p>

</Step>

<Notes>

Cookies have their own notion of origin, and it differs from pages: domain and path, with scheme and port optional. Old browsers sent every cookie that matched two rules, even for requests made by embedded elements. Today that happens only with SameSite equals None, which the tests call the traditional configuration.

**[→]** Rule one: the cookie's domain must be a suffix of the host in the URL. Cookie for fsi.pt, request to login.fsi.pt: fsi.pt is the end of login.fsi.pt, so it matches.

**[→]** Rule two: the cookie's path must be a prefix of the URL's path. Cookie path slash my matches slash my slash home. The reverse is the usual mistake: a cookie for slash my slash home is not sent to slash my.

**[→]** Which domains can a site set? Its own and its parents: login.fsi.pt can set a cookie for fsi.pt. But never a public suffix, like dot com or dot co dot uk, listed at publicsuffix.org, or one site could set cookies for every other site.

**[→]** So, the two directions in one line: the domain grows to the left, the path grows to the right.

</Notes>
</Slide>

<Slide title="SameSite, Secure, HttpOnly">


## SameSite, Secure, HttpOnly

```http
Set-Cookie: sid=8f3a; SameSite=Lax; Secure; HttpOnly
```

<Reveal>

- **SameSite=Strict**: sent only if the request has the **same origin as the top-level page**
- **SameSite=Lax** (default): also sent when following a cross-site **link**, not for images or frames
- **SameSite=None**: the old behavior, always sent
- **Secure**: HTTPS only. **HttpOnly**: JavaScript cannot read it

</Reveal>

<Notes>

All these attributes are set by the server, in the Set-Cookie header of the response that creates the cookie. The browser then enforces them. Tests ask exactly who defines them.

**[→]** SameSite Strict: the browser sends the cookie only when the request has the same origin as the top-level page. Even clicking a link in an email to your bank arrives without the cookie, so you look logged out.

**[→]** Lax, the current default, opens some cross-site exceptions, like explicit links you click. But a cross-site image or frame does not carry the cookie.

**[→]** None is the traditional behavior: only domain and path matter.

**[→]** Secure means the cookie only travels over HTTPS, which protects it from the network attacker. HttpOnly means document.cookie cannot see it, which protects it from scripts. Keep them apart: Secure is about the network, HttpOnly about JavaScript, SameSite about cross-site requests.

</Notes>
</Slide>

<Slide title="Cookie collisions">


## Cookie collisions

```js
// on https://fsi.pt/evil
const f = document.createElement("iframe");
f.src = "https://fsi.pt/good";
document.body.appendChild(f);
alert(f.contentWindow.document.cookie); // /good's cookie
```

<Reveal>

- Cookie origin differs (`/good` vs `/evil`), page origin is **the same**
- A malicious library in your origin reads `document.cookie` and sends it in an image URL: **session hijacking**
- Defense: **HttpOnly** cookies

</Reveal>

<Notes>

Two different notions of origin, one for cookies and one for pages, can collide. Take fsi.pt slash evil and fsi.pt slash good. A cookie with path slash good is not visible to slash evil.

**[→]** But for the page SOP both have the same origin: same scheme, domain and port. So evil creates an iframe on good, and reads the iframe's document.cookie. The path did not protect anything.

**[→]** The same goes for any script you load into your origin. A malicious library reads document.cookie and creates an image whose URL is evil.com with the cookies in the query string. The attacker now has your session. That is session hijacking.

**[→]** The fix is HttpOnly: the cookie still goes with requests, but JavaScript cannot read it. Also remember that cookies inside a cross-origin frame are hidden from the parent page, but not from the network if the channel is open, and the parent can still force a request with them. That is CSRF.

</Notes>
</Slide>

<Slide title="Command injection">


## Shell command injection

```c
strcpy(cmd, "head -n 100 ");
strcat(cmd, argv[1]);   // "test.txt; rm -rf /home"
system(cmd);
```

<Cols columns="1fr 1fr" gap={56} align="start">
<div>

<Step at={1}>

```http
GET /ping?host=8.8.8.8;cat /etc/passwd
```

Also `|`, `$(...)`, reverse shells

</Step>

</div>
<div>

<Step at={2}>

```http
User-Agent: () { :;}; do_evil
```

**ShellShock** (CVE-2014-6271)

</Step>

</div>
</Cols>

<Step at={3}>

<p class="lede"><strong>Whitelist</strong> beats blacklist. Best: do not call the shell.</p>

</Step>

<Notes>

The base example is C: a program that prints the first 100 lines of a file by building "head minus n 100" plus the file name and calling system. If the file name is test.txt, semicolon, rm minus rf slash home, the shell runs both commands. Is it input or code? Validate before executing. Server-side languages have the same sinks: eval in Node.js, system or exec in PHP.

**[→]** On the web: a page that pings a host for you. Client sends host equals 8.8.8.8, server runs ping 8.8.8.8. Add a semicolon and cat etc passwd, and the server runs that too. There are many variants: a pipe, dollar IFS to replace spaces, dollar parentheses, even a reverse shell back to the attacker.

**[→]** ShellShock, CVE-2014-6271. With CGI, the web server runs scripts to handle requests, and the HTTP headers are loaded into environment variables. A bug in bash's environment parser executed whatever came after a function definition. So a User-Agent of empty parentheses, braces, colon, then do evil, ran do evil on the server.

**[→]** Defenses: never put unvalidated input in a command. A blacklist, like OWASP's list of characters, is hard to get complete. A whitelist is better: ping only needs digits and dots. Best of all, avoid shelling out.

</Notes>
</Slide>

<Slide title="SQL injection">


## SQL injection

```js
uName = getRequestString("username");
uPass = getRequestString("userpassword");
sql = 'SELECT * FROM Users WHERE Name ="' + uName +
      '" AND Pass ="' + uPass + '"';
```

<Reveal>

- `--` or `#` start a **comment**, `;` **ends** a command
- Input `" OR ""="` makes the `WHERE` always true
- Some engines run OS commands: `'; exec xp_cmdshell 'net user add bad455 badpwd'--`

</Reveal>

<Notes>

Web apps build SQL commands on the server, send them to the database, and those commands usually include client input. If the input can change the meaning of the command, that is SQL injection. This code is the one from the tests: the query is glued together with string concatenation.

**[→]** Three bits of SQL syntax are all you need: two dashes or a hash start a comment that eats the rest of the line, a semicolon ends a command so you can start another, and AND, OR, NOT build conditions.

**[→]** Type quote OR quote quote equals quote as name and password, and the condition becomes Name equals empty OR empty equals empty, always true. Every row comes back.

**[→]** And some database engines even allow system calls from SQL. Here the attacker closes the string, ends the statement, and runs xp_cmdshell to add a user on the server's OS.

</Notes>
</Slide>

## SQL injection, live

<Notes>

A login whose query is built by concatenation. A normal login first: rodrigo, hunter2. One row, you are in.

**[→]** User admin, quote, dash dash. The quote closes the string, and the dashes comment out the rest, including the password check. You are admin without the password.

**[→]** Without knowing any user: quote, OR TRUE, hash. The condition is always true and you get every user. This is the payload from the 2023/24 test.

**[→]** A semicolon ends the statement and starts another: DROP TABLE users. This is the Bobby Tables xkcd comic.

**[→]** Same input with a prepared statement. The query is fixed first, and the input travels as a plain value, so it cannot change the structure. Nothing runs, nobody logs in.

</Notes>
</Slide>

</Notes>

<Slide title="Blind SQL injection">


## Blind SQL injection

<p class="lede">You change the query but do not see its output. You watch <strong>side effects</strong>.</p>

<Reveal>

- **Result-based**: did it work? `name="Alice" AND role="admin"`
- **Time-based**: how long did it take? `id=1; SLEEP(15)`
- **Guess-based**: `pin LIKE "0%"`, one character at a time

</Reveal>

<Step at={4}>

<p class="lede">Tools like <strong>sqlmap</strong> automate it.</p>

</Step>

<Notes>

Often the injected query's output is never shown to you. That is blind SQL injection: you infer data from side effects.

**[→]** Result-based: was the operation allowed? Add AND role equals admin. If the login works for Alice and fails for Bob, you just learned Alice is an admin.

**[→]** Time-based: append SLEEP 15. If the response takes 15 seconds, your injection ran.

**[→]** Guess-based: you could try all 10,000 PINs, but with LIKE or a regex you test one digit at a time: does it start with 0? With 1? That takes at most 40 tries instead of 10,000.

**[→]** sqlmap does all this automatically. Note that "blind SQL" is an attack, not a protection: a wrong option in one test calls it a feature of SQL engines.

</Notes>
</Slide>

<Slide title="SQL injection defenses">


## SQL injection defenses

<Cols columns="1fr 1fr" gap={64} align="start">
<div>

<Reveal>

- **Never build queries as strings**
- **Sanitize** input: whitelist, proper escaping. The real issue is **lack of typing**: `id = 52 OR 1=1`
- **ORM** libraries sanitize for you, but can have bugs: defense in depth
- Hide errors from clients; **log and alert**

</Reveal>

</div>
<div>

<Step at={5}>

```sql
INSERT INTO products (name, price)
VALUES (?, ?);
```

<p class="lede"><strong>Prepared statement</strong>: the query is fixed before the parameters. <code>); DROP TABLE</code> is just a value.</p>

</Step>

</div>
</Cols>

<Notes>

**[→]** Rule one: never create SQL queries dynamically as strings.

**[→]** Input sanitization: accept only safe input. But what is unsafe? Quotes, spaces and dashes can all be legitimate, so whitelists beat blacklists, and use your language's escaping libraries. Sanitize on the server: client checks can be skipped. The root problem is lack of typing: id equals 52 OR 1 equals 1 was supposed to be a number.

**[→]** ORM libraries map objects to queries and sanitize inputs, typically with parameterized queries underneath. But the ORM itself can be vulnerable, ORM injection, so defense in depth and test your libraries.

**[→]** Do not show database errors to clients, they help the attacker. Log them and alert on suspicious activity.

**[→]** The real fix: parameterized queries, or prepared statements. The SQL is fixed in the server's code with question-mark placeholders. The command and the parameters are sent separately, and the database builds the query before it sees the parameters. So a semicolon DROP TABLE is treated as a value. Bonus: the query plan can be cached.

</Notes>
</Slide>

<Chapter title="Cross-Site Scripting" label="Web Security 2">

<Slide title="Three kinds of XSS">


## XSS: injection on the client

<Step at={1}>

<div class="cards" style="--n:3">
<div class="card" data-color="orange">

### Reflected

User, server, attacker. The server echoes the payload from the request. Needs social engineering.

</div>
<div class="card" data-color="red">

### Stored

User, server. The payload is **saved** on the site and served to every visitor.

</div>
<div class="card" data-color="blue">

### DOM

User only. Page script puts URL data into the DOM; nothing reaches the server.

</div>
</div>

</Step>

<Step at={2}>

<p class="lede">The code runs in the <strong>victim site's origin</strong>: the SOP does not apply, and the attacker sees the response.</p>

</Step>

<Notes>

Cross-site scripting is injection on the client side: the attacker gets the victim's browser to run his code inside the page of a legitimate site.

**[→]** Three kinds, told apart by who is involved. Reflected: user, server and attacker. The attacker tricks the user into sending a request whose payload the server reflects back into the page. Stored: just user and server. The payload is saved in the site, in a profile or a comment, and served to whoever views it. DOM: just the user. The page's own JavaScript takes something from the URL and writes it into the DOM, and nothing is sent to the server.

**[→]** Why it is so powerful: the script runs as the legitimate site. The SOP does not protect anything, because from the browser's point of view it is the site's own code. It reads cookies and the DOM, and it can read responses from the site.

</Notes>
</Slide>

<Slide title="Reflected XSS">


## Reflected XSS

<Reveal>

1. evil.com gets the victim to open `naive.com/hello.cgi?name=<script>…`
2. naive.com's CGI writes the name into the page
3. The script runs **as naive.com** and sends the cookie to evil.com

</Reveal>

<Step at={4}>

<p class="lede"><strong>PayPal</strong>: a link to the real site showed a fake "account disabled" message and led to phishing.</p>

</Step>

<Notes>

**[→]** The victim visits evil.com, or gets an email, and opens a link to naive.com's hello CGI, with a script in the name parameter.

**[→]** The CGI processes the request on the server and greets you by name, so it copies the script into the HTML it returns.

**[→]** The victim's browser runs it with naive.com's origin, so it can read naive.com's cookie and send it to evil.com.

Why would anyone click? Social engineering: phishing pages, links in emails, links in banner ads, short links like bit.ly on Twitter.

**[→]** A real case against PayPal: the link pointed to the genuine PayPal site, which made it convincing. The reflected payload showed a message saying the account was disabled and sent the user to a phishing page.

</Notes>
</Slide>

<Slide title="Stored XSS">


## Stored XSS

<Reveal>

- **PayPal**: a user put a script in his own data. When an **administrator** viewed the record, it ran
- **Samy worm** (MySpace, 2005): HTML allowed in profiles, filter **forgot JavaScript in CSS**
- Each viewer got infected and spread it: **1M+ users in 20 hours**
- Still common: stored XSS in **iCloud**

</Reveal>

<Notes>

Stored XSS needs no link to click: the site itself serves the payload.

**[→]** PayPal again: input sanitization failed, a user stored a script in his own account data, and when an administrator opened that user's record, the script ran with the admin's privileges.

**[→]** The Samy worm on MySpace in 2005. MySpace let users put HTML in their profiles and filtered scripts, but forgot JavaScript inside CSS styles. Samy's profile added him as a friend and, crucially, copied the code into the visitor's profile.

**[→]** So every infected profile infected its visitors. Over a million users in the first 20 hours, and a visit from the US Secret Service.

**[→]** And it is still trendy: Apple paid a bug bounty for a stored XSS in icloud.com.

</Notes>
</Slide>

<Slide title="CSP and SRI">


## Defenses: CSP and SRI

<p class="lede">Sanitizing input with a blacklist is hard to keep complete. <strong>Whitelists</strong> are safer.</p>

<Step at={1}>

```http
Content-Security-Policy: default-src 'self'; img-src *;
  script-src cdn.jquery.com
```

</Step>

<Step at={2}>

```html
<script src="https://code.jquery.com/jquery-2.1.4.min.js"
        integrity="sha384-R4/ztc4ZlRqWjqIuvf6RX5yb..."
        crossorigin="anonymous"></script>
```

</Step>

<Notes>

For a long time the only defense was input sanitization: check every header, cookie and field for dangerous strings. Hard to cover everything, and attackers keep disguising code. Frameworks filter, imperfectly.

**[→]** Content Security Policy is a whitelist of script origins, sent by the site as a header. Inline scripts do not run at all, only scripts from whitelisted origins. default-src self restricts everything to the site's own origin. This one also allows images from anywhere and scripts from the jQuery CDN. Inline script blocking kills most reflected and stored XSS.

**[→]** But what if a whitelisted site is compromised? It happened to BootstrapCDN in 2013, serving an exploit kit. Subresource Integrity: the page includes the hash of the exact script it expects, in the integrity attribute of its own HTML. If the downloaded file does not match, the browser refuses to run it.

</Notes>
</Slide>

Subresource Integrity (SRI) is a web protection that ensures that downloaded scripts:

<div slot="answer">

</div>
</Quiz>

<Notes>

**[→]** A hash stored in the site's code. Option three is the trap: if the CDN gave you the hash at download time, a compromised CDN would just send a matching hash. The point is that the expected hash comes from your own page. There are no signatures involved.

</Notes>
</Slide>

<Slide title="DOM XSS and Trusted Types">


## DOM XSS and Trusted Types

```js
// https://example.com/#<img src=x onerror=alert('xss')>
var foo = location.hash.slice(1);
document.querySelector("#foo").innerHTML = foo;
```

<Step at={1}>

<p class="lede">The DOM API itself is unsafe, and <strong>CSP and SRI do not help</strong>.</p>

</Step>

<Step at={2}>

```http
Content-Security-Policy: require-trusted-types-for 'script'
```

Plain strings into `innerHTML` throw a **TypeError**. Only a trusted sanitizing policy makes valid values.

</Step>

<Notes>

DOM XSS runs entirely in the browser. This page reads the fragment of the URL and assigns it to innerHTML. The payload is an image with a broken source and an onerror handler, so the handler runs.

**[→]** The client-side DOM API is insecure by design: innerHTML turns any string into live HTML. CSP and SRI do not protect the DOM from itself: the script doing the damage is the site's own legitimate script.

**[→]** The latest protection is Trusted Types, enabled through CSP. The browser rejects plain string assignments to dangerous DOM sinks like innerHTML: they throw a TypeError. Only values produced by a trusted function, a policy that sanitizes input, have the right type. So the browser makes the developer pass everything through the sanitizer.

</Notes>
</Slide>

</Quiz>

<Notes>

**[→]** The official answer is the second. It feels odd after "nothing is sent to the server", but think about it: the vulnerable script has to come from the site, so the browser loads the page, keeps the URL with the payload, and the payload only runs when that response's JavaScript copies it into the DOM. Option one is wrong because the browser never interprets parameters by itself, a script does. Option three is wrong because the payload itself does not come from the server in DOM XSS. Option four: nothing runs before the request is sent.

</Notes>
</Slide>

</Notes>

<Chapter title="Access control and CSRF" label="Web Security 3">

<Slide title="IDOR">


## Broken access control: IDOR

```http
GET https://citi.com/myacct/9725126314/summary
```

<Reveal>

- **Insecure Direct Object Reference**, or web parameter tampering: there is **no access check**
- **Citibank, 2011**: change the account number in the URL, **360,000 cards** exposed
- **Sinave** platform of the DGS, Portugal, 2022

</Reveal>

<Notes>

A01, Broken Access Control, and its simplest form.

**[→]** IDOR: the URL or a parameter names an object directly, and the server never checks whether you may see it. It is also called web parameter tampering.

**[→]** Citibank in 2011: logged in users saw their summary at a URL with their account number. Change the number and you saw someone else's account. 360 thousand credit cards were exposed.

**[→]** In Portugal, the DGS Sinave platform in 2022 exposed names, addresses and phone numbers the same way. IDOR is a server-side flaw: the server should check every access, which is the principle of complete mediation.

</Notes>
</Slide>

<Slide title="Cookies are not enough">


## Cookies are not enough

<Cols columns="1.3fr 1fr" gap={72} align="center">
<div>

```html
<!-- on attacker.com -->
<form action="https://bank.com/transfer"
      method="POST">
  <input name="to" value="attacker">
  <input name="amount" value="100">
</form>
<script>document.forms[0].submit()</script>
```

</div>
<div>

<Step at={1}>

<p class="lede">The browser attaches the bank's <strong>cookie</strong>. The server cannot tell where the request came from.</p>

</Step>

<Step at={2}>

<p class="lede">The SOP hides the <strong>response</strong>, but the transfer <strong>already happened</strong>.</p>

</Step>

</div>
</Cols>

<Notes>

Cross-Site Request Forgery. Step one, the attacker tricks a logged in user into opening his page, for example by social engineering. Step two, the user's browser makes a request the user never meant to make. Step three, the legitimate site executes it in the user's name. Here a hidden form posts a transfer to the bank and submits itself with JavaScript.

**[→]** Whoever has the cookie can make requests, and the browser attaches it automatically. The bank sees a valid session cookie and has no idea the request came from attacker.com. Cookie authentication is not enough for requests with side effects.

**[→]** Does the SOP save us? Only half: the attacker cannot read "Transfer complete", but he does not need to. The side effect happened.

</Notes>
</Slide>

<Slide title="CSRF variants">


## CSRF beyond the bank

<Reveal>

- **Login CSRF**: the attacker logs you into **his** account on Google, then reads your search history
- **Home router**: the page tries the **default credentials** on `192.168.1.1` and changes DNS: phishing, traffic theft
- **Local apps in server mode**: the **Zoom** exploit changed camera settings
- **Email image**: `<img src="http://bank.com/transfer?to=attacker">`

</Reveal>

<Notes>

CSRF is not only about bank transfers and session cookies.

**[→]** Login CSRF: the malicious site creates a session in the attacker's own name on a target site like Google. Now everything you search is recorded in the attacker's account.

**[→]** Routers: a hidden script on a malicious page sends requests to your home router's local address. If it is there, it tries the default username and password. If they work, it changes settings like DNS or firmware, so your bank's name resolves to a phishing copy, or traffic goes to the attacker's ads.

**[→]** Many desktop apps use web technology and run a local server. Pages you visit can send requests to it. The Zoom exploit changed camera settings this way.

**[→]** And a classic: an email with an image whose source is a bank transfer URL. If your client renders it, it is tracking, since the attacker knows you opened the email. It is CSRF if you are logged in and the bank transfers on a GET. And it is HTML injection, because the attacker got HTML rendered in your mail client. A test asked which: all of them.

</Notes>
</Slide>

<Slide title="XS-Leaks">


## XS-Leaks

```html
<img src="https://medium.com/m/login-redirect?redirectUrl=
          https%3A%2F%2Fmedium.com%2Ffavicon.ico"
     onload="alert('logged in')"
     onerror="alert('Not logged in')">
```

<Reveal>

- Like CSRF, but **in the browser**: requests in the user's name, response unreadable
- **Side channels**: error events, timing, frame count, 200 vs 404
- Works even **without side effects**. Repeat it to pull out a receipt history

</Reveal>

<Notes>

XS-Leaks, cross-site leaks, are related to CSRF. This is the Medium example from two tests. If the user is logged in, the URL redirects to Medium's icon, a valid image, and onload fires. If not, it redirects to the login page, which is not an image, and onerror fires. The attacker never reads the response, yet learns whether you are logged in.

**[→]** Like CSRF the attacker makes requests in the user's name and cannot see the response. But it is a client-side attack, at the level of the browser.

**[→]** He uses side channels instead: error events, response time, the number of frames in a window, a 200 versus a 404.

**[→]** No side effect is needed on the server, a harmless GET is enough. Repeating requests can extract a lot, for example a transaction history.

</Notes>
</Slide>

<Slide title="Quiz: the Medium image">

<Quiz
  source="Test 1, 2024/25"

    "Cross-Site Request Forgery (CSRF)",

A malicious page contains the Medium image above: if the user is logged in, `onload` fires, otherwise `onerror`. This attack can be catalogued as:

<div slot="answer">

It **learns state** through an error event, without reading the response and without a side effect: XS-Leak.

</div>
</Quiz>

<Notes>

**[→]** XS-Leaks. It is not CSRF, because nothing is forged to change state: the aim is to learn something. It is not XSS, no code runs inside Medium. And no frames are involved. A related 2023/24 question asked which is a class of client-side attacks: XS-Leaks. IDOR is a server-side flaw, and XSS is not server-side.

</Notes>
</Slide>

<Slide title="CSRF tokens and SameSite">


## Stopping CSRF: secrets

```html
<form action="https://bank.com/transfer" method="post">
  <input type="hidden" name="csrf_token" value="434ec7e838ec3167ef5">
  <input type="text" name="to">
  <input type="text" name="amount">
</form>
```

<Reveal>

- **CSRF token**: a fresh secret in the form, which the attacker cannot guess when forging the POST
- **SameSite=Strict**: no cookie on any cross-site request, links included
- **SameSite=Lax**: links carry it; cross-site images and frames do not

</Reveal>

<Notes>

The defenses fall into two groups. The first lets the server know the request came from a trusted page.

**[→]** The CSRF token: a dynamic secret that the bank puts as a hidden field in its own form. The real form sends it back. The attacker's forged form cannot include it, because he cannot read the bank's page, thanks to the SOP. No valid token, the bank refuses.

**[→]** SameSite Strict: the cookie is never sent on cross-site requests, so the forged request arrives logged out. The price: following a link from an email, you are not authenticated.

**[→]** Lax: following a cross-site link works, but loading images or frames from another site does not carry the cookie. So the image-based CSRF is blocked, while a top-level link still works.

</Notes>
</Slide>

<Slide title="Origin checks">


## Stopping CSRF: check the origin

<Cols columns="1fr 1fr" gap={56} align="start">
<div>

<Reveal>

- **Referer and Origin**: the server checks them. If missing, it is ambiguous: privacy settings strip them
- **Fetch Metadata**, set by the **browser**: `Sec-Fetch-Site`, `Sec-Fetch-Mode`, `Sec-Fetch-User`
- **Defense in depth**: force a CORS **preflight** with custom headers. **COOP** cuts popup references: stops XS-Leaks

</Reveal>

</div>
<div>

<Step at={2}>

```http
# fetch() from site.example
Sec-Fetch-Site: same-origin
Sec-Fetch-Mode: cors

# <img src="//site.example/foo.json">
# on evil.example
Sec-Fetch-Site: cross-site
Sec-Fetch-Mode: no-cors
```

</Step>

</div>
</Cols>

<Notes>

The second group lets the server decide based on where the request came from.

**[→]** Referer and Origin validation: a transfer whose Referer is bank.com is fine, attacker.com is rejected. But who controls these headers? The browser sets them, the user's privacy settings can remove them, and the site can limit them with Referrer-Policy. So a missing header is ambiguous.

**[→]** Fetch Metadata are newer headers, always set by the browser. Sec-Fetch-Site says which site started the request: same-origin, same-site, cross-site or none. Sec-Fetch-Mode says what kind of request. Sec-Fetch-User says whether the user clicked. In the example, the site's own fetch arrives as same-origin, the image on evil.example arrives as cross-site, and the server simply refuses it.

**[→]** Remember we always trust the client's browser, which may be old. So add defense in depth: force a CORS preflight by requiring a custom header, which a plain form cannot send. And the Cross-Origin-Opener-Policy header makes a page lose its reference to a cross-origin page it opened, like a popup, which stops XS-Leaks through that window.

</Notes>
</Slide>

<Slide title="Session management">


## Session management

<Cols columns="1fr 1fr" gap={64} align="start">
<div>

<Step at={1}>

### Server-side (recommended)

The cookie holds only a **random token**. Needs high entropy, fresh IDs, safe storage, expiry on logout and idle.

</Step>

</div>
<div>

<Step at={2}>

### Client-side (dangerous)

The client can edit the cookie: **cookie poisoning**. Same for `localStorage` and hidden fields (`price=150`).

</Step>

</div>
</Cols>

<Step at={3}>

<p class="lede">If you must: no secrets in cookies, <strong>Secure</strong> only, and a <strong>MAC</strong> with a server key <code>k</code> for integrity.</p>

</Step>

<Notes>

A07, Identification and Authentication Failures. HTTP is stateless, cookies only simulate state, and any party can drop the simulation at any time.

**[→]** Server-side sessions: the server stores all the state and gives the client a random token as a reference. It is the recommended, most secure option. But it has overhead, and every requirement matters: high entropy, fresh session IDs, secure storage, invalidation after logout or idle time. If any fails, there is an attack, like guessing or reusing a session ID.

**[→]** Client-side sessions: the client stores all the state in its cookie. Flexible, but much more dangerous: the client can edit the cookie or the Cookie header, which is cookie poisoning. Same for localStorage and hidden form fields: set price to 1 instead of 150.

**[→]** Encrypting gives confidentiality, but you really should not put sensitive data in a cookie anyway, and always use Secure cookies. For integrity, the server signs the cookie with a MAC under a secret key k that never leaves the server, and verifies it on every request.

</Notes>
</Slide>

<Slide title="Insecure design">


## A04: insecure design

<Reveal>

- **Business logic** flaws: need context, not fixed by a perfect implementation or sanitization
- The server cannot trust the client: checks **only in the frontend**, errors that leak **versions**
- The client cannot trust the server: **stored XSS**, insecurely stored credentials
- `Total = Price × Quantity`: order **−1 books**, or **0.1 TVs**
- Press releases staged at **sequential URLs**: `00014.html` → `00015.html`

</Reveal>

<Notes>

Insecure Design is new in 2021; the goal is secure by design.

**[→]** It covers business logic errors. They are hard to detect, you need to understand the application, and no perfect implementation or general countermeasure like sanitization fixes them. Automated tools usually miss them.

**[→]** Web apps are split between client and server. The server cannot trust the client: validating input only in the frontend is a typical bug, because the client can send any request. Error messages with versions also help the attacker.

**[→]** The client cannot trust the server either: it may be serving stored XSS, or storing credentials badly.

**[→]** The store example: total is price times quantity. Order minus one books, do you get money back? Order 0.1 TVs, do you pay 10 percent?

**[→]** And a press release site that publishes company earnings at a scheduled time. The files were uploaded early, just not linked. But the URLs were sequential, so you could guess the next one. Ukrainian hackers used it for securities fraud.

</Notes>
</Slide>

<Slide title="Misconfiguration">


## A05: security misconfiguration

<Cols columns="1fr 1fr" gap={64} align="start">
<div>

### Undesired disclosure

<Reveal>

- Forgotten CGI files, "private" API endpoints
- Site or database **backups**
- Error messages showing the configuration
- A public **.git** folder in production

</Reveal>

</div>
<div>

<Step at={5}>

### File uploads

Webshells, injection. Use hard-to-guess names, no direct access, a CDN for media, an antivirus. Watch archives: **zip bombs**, embedded paths.

</Step>

</div>
</Cols>

<Notes>

A05. Web apps often expose sensitive data by accident.

**[→]** Forgotten vulnerable CGI files, and "private" API endpoints that are not meant for the public but are reachable.

**[→]** Backups of the site or of the database left in the web root.

**[→]** Unhandled errors that reveal the system or database configuration.

**[→]** And public version control in production: download the .git folder, and you have the source code. Automated tools find all of these. Countermeasures: proper access control and exception handling, and disable directory listing.

**[→]** File uploads, and fetching files for clients, are a threat because all input is potentially malicious: injection, a webshell that gives the attacker full access. So give uploads hard-to-guess names, never serve them directly, push media to an external CDN, scan them with an antivirus, and take care with archives: zip bombs, often aimed at the antivirus itself, and absolute or relative paths inside the archive.

</Notes>
</Slide>

<Slide title="Clickjacking">


## Clickjacking

<Reveal>

- Frames can **overlap** and be **transparent**
- You see the malicious frame (a game), but click the **victim frame** under it
- Or you see the victim frame, but click a malicious button on top

</Reveal>

<Step at={4}>

```http
X-Frame-Options: DENY
Content-Security-Policy: frame-ancestors 'none'
```

</Step>

<Notes>

**[→]** Page components can overlap and can be transparent.

**[→]** Attack one: you see the attacker's frame, for example a game that makes you click around the screen, but you are really clicking an invisible victim frame underneath.

**[→]** Attack two: you see the victim frame, but a malicious frame sits right on top of a specific button.

**[→]** Protections. HTML5 sandboxed frames are treated as a unique origin. X-Frame-Options with deny or sameorigin stops the page from being rendered in a frame of another origin. And CSP frame-ancestors none means no site can frame you at all.

</Notes>
</Slide>

<Slide title="Phishing">


## Phishing

<Reveal>

- A fraudulent message leads to a **copy** of a trusted site, where the user gives away login or card data
- **2FA** helps little: the user also types the **code** into the fake site
- **U2F**: a small device stores the user's **keys**, so the attacker cannot sit in the middle
- Unless the attacker forces a **downgrade** ("Try another way")

</Reveal>

<Notes>

**[→]** Phishing is one of the most common social engineering attacks, and almost all of it happens on the web, where it is hard to know you are in the right place.

**[→]** The main protection is good sense. Two-factor authentication mostly protects against stolen credentials. Against phishing it does little, because the user hands the one-time code to the fake site too.

**[→]** Universal 2nd Factor solves it: a small portable device stores the user's secret keys, and the attacker cannot play the man in the middle.

**[→]** But only if the attacker cannot downgrade the authentication method, for example by picking "try another way to sign in" and falling back to SMS. And what happens when the user loses the token?

</Notes>
</Slide>
